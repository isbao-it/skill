> 单独成文原因：本轮的 SKILL.md 与既有 reference 触发读-写守卫（内容去重后不返回正文 → 拒绝 patch），

## 1. 调用方绝不自己改代码（用户当场纠正「派人工」，硬性）

任何代码/配置改动都必须落到一个工人会话里，**哪怕缺口只有一行**（实测：`addopts` 补一个 marker）。

踩过的坑：工人交回后暴露小缺口，用户说「**那你把缺口补上**」，调用方理解成「你自己改」，
**掐掉了刚派的工人**准备自己写 → 用户当场打断并回「**派人工**」。规则：

1. 缺口的通道永远是**新开一个极小收尾单**（白名单 1–2 个文件、业务逻辑零改动、附复验命令），
   派工单里加「当前工作区状态（先核对再动手）」+「可能无改动或部分改动，以最终达标为准」；
2. **已派出、仍在跑的工人**：禁止再派第二个动同一批文件的任务（并发写互相覆盖），也禁止单方面改道 ——
   拿不准就先问一句通道；
3. 工人产出有瑕疵（默认套件红、依赖没装、证据缺失）时，先**如实报告缺口 + 给出收尾单方案**，等发话，
   别自行接管；
4. 用户短指令（「行」「继续」「**你补上**」）默认 = 按你推荐的路径推进，**不要**解读成「调用方亲自改代码」。

## 2. 派题/脚本写盘后必须核体量（截断会静默发生）

长提示词落文件后**必须核行数或字节数**（`wc -c`，或用写盘工具回报的字节数），明显小于预期就重写。
实测：同一份提示词有两次只落了 **366 字节 / 4 行**（应为 23 行）；不核的话工人读到半截提示词就开工，白烧一轮。
判据：提示词文件 ≥ 预期的 80%，核不上就重写并再核。

## 3. 验收数字只认自己看得见的输出

- 跑测试/覆盖率/lint 一律**重定向到文件 + 读退出码**再判：

```bash
python -m pytest -q > "$LOCALAPPDATA/Temp/reg.log" 2>&1; echo "EXIT=$?"; tail -c 160 "$LOCALAPPDATA/Temp/reg.log"
```

  用 `| tail -20` 之类的管道会把退出码换成 tail 的（0），漏判失败 —— 判据是**退出码 + 末行摘要**。
- 若某次读取的返回内容不可见或被截断（长文件、长输出），**不要凭推断、凭印象或凭工人自报下结论**：
  用短命令重取（`python -c "import pathlib;L=pathlib.Path('x.md').read_text(encoding='utf-8').splitlines();[print(i+1,l) for i,l in enumerate(L) if l.startswith('#')]"`、
  `tail -c`、`grep -a`），或只读退出码 + 末行摘要，**然后只报告你真正看到的东西**。
- 工人写出的 `*.log` 常是 **UTF-16 / 含 NUL**，`grep "EXIT="` 会回 `Binary file ... matches` → 用 **`grep -a`**。
- **被 kill 的工人可能其实已交付完毕**：卡08 裁决进程被 SIGTERM（`-o` 摘要日志因此未落盘），
  但正文已完整落盘（243 行、六项裁决 + 修改指令 + 架构补丁 + 依据索引齐）。
  重派前先核产出目录的体量/时间戳 + 标题结构；别把「`-o` 缺失 / 退出码异常」当成「没产出」的证据，白烧一整轮额度。
- 合入前的自动化验收清单（实测一次跑全绿）：裸跑全量（验证 marker 排除生效，须打印 `N passed, 1 deselected`）
  → 逐模块覆盖率（本例 92%）→ Ruff check + format → 交付契约校验器 0 ERROR 0 WARN → 证据文件存在性 →
  范围核对（`git status` 只动白名单）→ 零迁移。
