# 额度预算、独立会审与"不可命令行派工"的 harness

> 来源：2026-09-15 一次真实的额度危机处理 —— 用户在跑「架构师 + PM + 工人」多 agent 开发流水线时
> 抱怨"额度消耗太快、测试部分消耗大"，并要求把 GUI 型 harness（DeepSeek Harness Desktop）纳入。
> 本文是该次审计 + 方案会审后沉淀下来的可复用结论。**凡标「未验证」的，不要当结论用。**

## 一、诊断：额度到底烧在哪（有脚本，别凭感觉）

跑 `scripts/codex_quota_audit.py`（本目录同级的 `scripts/`）。要点：

- 单会话成本 ≈ **Σ(每轮重放的上下文)** ≈ **轮数 × 平均每轮上下文长度**。
- 本机实测（42 个会话）：input 49,684,492 / output 542,060 = **92 : 1**；cached 45,331,840（91%）。
- 单卡峰值：98 轮 × 平均 134k = **12,992,812 input**，一个会话吃掉全项目 26%。
- 结论：额度烧在「上下文每轮重放」，不在「写代码」（output 只占 ~1%）。所以省额度 =
  **压轮数 + 压每轮上下文**，两件都要做。

**过度主张警告（被独立会审纠正过）**：
- 91% 缓存命中 **≠ 省 91% 额度**；token 数与订阅额度不是同一口径，缓存读写在两套计费下规则不同。
- 因此**不要说"已省 70%"**，只能说"输入下降"。要声称额度节省，必须在隔离时间段做对照读数。
- "测试部分最耗额度"这类判断**需要分项统计**（测试编写 / 执行 / 失败诊断 / 读文档）才成立，
  否则只是印象。本机当时**未证实**。

## 二、派工合同里的额度预算（建议初值，10 张可比卡后校准）

| 阶段 | 调用次数目标 | 累计 input 目标 | 干预点 |
|---|---:|---:|---|
| 架构单议题 | 15–25 | ≤1,500,000 | 30 次报告；40 次检查点暂停 |
| 双卡出卡与修订 | 10–15 | ≤600,000 | 超目标先查重复引用与范围漂移 |
| 执行（TDD + 定向验证） | 15–25 | ≤1,500,000 | 30 次报告；40 次或 200 万先到者暂停 |
| 独立复核 | 5–8 | ≤400,000 | 最多 10 次，未完成项交回调度方 |
| 单卡全链路 | — | ≤3,000,000 | 含 ~50 万交接/返工余量 |

补充：首次调用输入目标 ≤30k；连续 3 次输入 >80k → 查"误读大文件 / 历史膨胀"。
**超限触发诊断，不触发少测或仓促交付。**

派题必备五条（同步进 SKILL.md 第二节）：
① 轮数预警线（到线报告等指令，**宁可拆卡不许赶工**）② 读取白名单（≤6 个任务文件，白名单外
**先报告索取，禁止猜接口**）③ 输出重定向、只回读退出码 + 末尾摘要 + traceback 片段
④ 全量回归/覆盖率/lint 归调用方本地跑 ⑤ `summary.json` + 结论 ≤150 行、明细进 `details/`。

额度调度配额（调度用，不是平台模型）：架构/出卡留 30%，关键复核与救火留 20%，
普通执行最多用剩下 50%；可见剩余 <20% 时暂停普通执行。

## 三、改完规则必须跑一次"独立会审"

同一作者改的规则，**自己看不出内部冲突**。做法：把改动后的全部规则文件交给第二个 agent
（只读、禁止写），任务只要三件事：① 逐条找矛盾（权威原文 vs 派生文件 vs 模板）② 指出
过度主张/未验证收益 ③ 指出会让质量下降的条款。

本机实测战果（一次会审）：
- **5 处过度主张被纠正**：缓存≠额度、未证实的"测试最耗"、8k+6k 算成 15k（应 14k）、
  "超过 8 条用例即拆卡"会诱导少测（应改 ≤8 个**行为组**、参数化样本不设限）、
  "只 grep FAILED"会误判通过（应看退出码）。
- **7 条内部冲突**：最典型的是"全量回归由谁跑"在权威原文（调用方跑）与测试卡模板
  （工人跑覆盖率+回归）里写法相反 —— 工人会照旧烧额度。

**教训：改规则时，"权威原文 / 摘要文件 / 模板 / skill"四层必须一次改齐，否则工人读到的
是旧口径。** 派这种会审时同样给薄简报 + 读取白名单 + 禁止写文件，实测成本从同类会议的
321 万 input/31 轮降到 **23 万/7 轮**。

## 四、A/B 判定：同窗口续写 vs 新开会话

直觉"在同一个窗口接着写代码更省"**未被数据支持**：同窗不会减少"每轮重放"这个乘法项，
反而让历史（讨论、否决方案）继续进上下文。判据：

- 只有 `R_r·Ī_r < R_n·Ī_n` 才省输入（续写平均输入是新会话 2 倍时，调用次数必须降到一半以下）。
- 实验：**12 对固定任务**（A = 出卡会话 resume 执行，B = 新会话只读已审双卡），
  控制模型/推理档位/CLI 版本/代码初态/卡版本/依赖/机器/超时，两份独立代码副本，6 对先 A 6 对先 B。
- 采用 resume 的门槛：配对 input 比值中位数 **≤0.80** 且 ≥9/12 对更省、耗时不增 >10%、质量全过门槛。
- 声称"额度更省"另需 ≥8 对有效额度读数（配对比值中位数 ≤0.80），否则只能说"输入下降"。
- 未达阈值 → 保留"新会话"默认；失败/超时/换人样本必须计入成本，不能只统计成功执行。

## 五、质量保险与度量（证明"省额度不降质量"）

| 指标 | 初始阈值 |
|---|---|
| 首次验收通过率 | 新流程不低于基线 >5 个百分点 |
| 打回次数 | 分类记录（需求冲突 / 漏测 / 实现错误 / 证据缺失） |
| 返工次数 | 每卡平均不高于基线 +0.2 |
| 逃逸 bug（验收后 14 天归因） | 严重缺陷 0 |
| 关键漏测 / 越界放水 | 0（出现即暂停该执行路线） |
| 效率（每个验收任务累计 input） | 下降 ≥30% |
| 人工负担 | 中位数不增 >10% |

省下的额度**拿出一部分换一双眼睛**：每卡 1 次独立复核（只读契约 + 真实 diff + 测试）。
复核者发现缺口只报问题，改代码属于另一次获批的修复步骤。

## 六、GUI 型 harness（无 CLI）能不能当工人

实测对象：DeepSeek Harness Desktop（Electron GUI，`@deepseek-ai/dsh-base` + `dsh-web-app`，
cordis 插件框架 + 自有插件市场；`provider: deepseek-official`，凭据是**账号登录**而非 API key，
故额度与 ChatGPT/Codex 解耦；`networkExposure: loopback`；npm 上同名 CLI/TUI 包仅占名未发布）。

三路对比（结论：**先手动，别先造桥**）：

| 路线 | 可行性 | 脆性 | 决策 |
|---|---|---|---|
| GUI 手动 | 已知有入口；读写/跑命令能力**未验证** | 人工可绕过界面变化，但会抄错路径、漏结果 | **先采用**（先做资格预检：能跑 1 条定向测试并取到退出码，才派正式卡） |
| computer_use 后台驱动 | **未验证** | 焦点/弹窗/遮挡/登录失效都会中断 | 不承诺无人值守 |
| 自研插件暴露本地 API | 插件框架 + loopback 路由 **≠ 现有任务 API** | 受内部协议与升级影响 | 暂缓单独立项；门槛：手动累计 ≥10 张合格卡且人工搬运中位数仍 >5 分钟 |

硬规矩：**绝不复用或外泄桌面登录令牌**；若该 harness 不输出 token usage，记 `null` 并写
"未提供"，用验收率/人工分钟/耗时/账号额度读数评价，**不要编造 token 节省比例**。

## 七、两个操作细节

- **非 git 目标的越界检测**：派工目标不是仓库（笔记库、文档库）时 `git status` 用不上。
  派工前 `os.walk` 落 `{相对路径: [大小, mtime]}` 快照，收工后重跑并 diff，得到
  新增/删除/改动三张清单 —— 只应有本次约定的新文件。派题里同时写死
  "除该文件外不得创建、修改、删除、移动任何文件（含文档维护与临时产物清理）"。
  本机实测：靠这条查出过一次工人自行删除 3 份未入库文档的事故。
- **编辑用户文件保持原行尾**：用户文件可能 LF/CRLF 混用，用 patch 类工具会把 LF 文件写成 CRLF，
  产生整文件 diff 噪音。做法：`open(p,'rb')` 读 → 记 `b'\r\n' in raw` → 解码后编辑 →
  写回时按记录的行尾还原（`t.replace('\n','\r\n') if crlf else t`）→ 二进制写。
  改动前把原件复制到 temp 作回滚点（非 git 目录没有别的退路）。
