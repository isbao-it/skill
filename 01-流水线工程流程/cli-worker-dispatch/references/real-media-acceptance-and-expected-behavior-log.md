# 真素材实测与「预期行为」落档（2026-09-18 实测补充）

补充（不替代）`acceptance-gate-and-error-code-triangulation.md`（闸门 + 错误码三角定位）与
`dispatch-mechanics-and-default-suite-gate.md`（裸跑默认套件）。

## 一、自动闸门全绿 ≠ 交付可用

自动闸门（定向 + 覆盖率 + **裸跑全量** + Ruff + 校验器 0/0 + 范围核对 + 证据存在性）能拦住的，
是「结构化错误」：越界、漏跑、断言放宽、契约漂移。它**拦不住**「行为在真素材上不对」这类缺陷。

实测案例：验收全绿之后，用户点名要试真视频
`视频测试/尼罗河花园.mp4`（60.9s 容器 / **74.5s 音频** / AAC 48k 立体声 / 3.4MB，在适配器限额内）。
把 mp4 解成 16k 单声道后走**真适配器端到端**，暴露两件事：

1. **固定 `vad_filter=True` + 唱歌/纯 BGM → 0 段**：同一文件 `vad=False` 出 **21 段歌词**、
   `vad=True` 出 **0 段** → 是**素材判定**（Silero VAD 只留说话声），不是引擎故障。
   但适配器把「0 段」与「引擎不可用」收敛成同一个码（`asr_unavailable`）→ 排查被误导到
   网络/模型缓存/GPU 驱动上去，绕了很远才发现真相。
2. **输出繁简混排**：同一份输出里 `卻不曾發覺`(繁) 与 `满天飞雪`(简) 并存 →
   下游若用简体词库/关键词打分，会**静默漏匹配**（不报错，只是数字变小）。

**判据**：这两条在定向/全量/Ruff/校验器里**一条都测不出来** —— 它们只服从于真实素材与下游语义。

## 二、真素材实测的三条纪律

1. **合成 fixture 只能验「链路通」，不能当质量判据**。合成 TTS 机器音（`local-flite-pinyin-tts`）
   被 medium 模型识别成「你好,我是西元西北西西」——fixture 通过的用例，说明不了任何质量。
   质量/行为类问题**必须用用户自己的真素材**跑（用户往往手上就有：视频、录音、截图）。
2. **一次真素材跑完，当场把现象三分并落档**（这是本文件存在的原因）：

   | 判定 | 本次实例 | 落档动作 |
   |---|---|---|
   | **预期行为**（按需求不该做） | 歌/环境音不要求转写 | 写明「维持 `vad_filter=True`，0 段属预期」+ 依据（用户拍板） |
   | **待修缺口**（下游会被坑） | 繁简混排 → 简体词库静默漏匹配 | 记「待出卡：输出统一简体」，额度恢复后走流程 |
   | **低优先级观察**（语义不准但无害） | 0 段报 `asr_unavailable` | 记录不改代码，防后人重复误判 |

3. **用户说「这个不用做」同样是决策**，要落成「预期行为 + 依据」写进决策/快照文件；
   **只写在聊天里等于没记** —— 下一次（或下个月的自己）会把它当缺陷再报一遍，重复排查一遍。

## 三、低成本复现配方（可抄）

```python
# 1) 任意容器 → 16k 单声道 s16 wav（resampler 必须 flush，否则尾部丢帧）
# 2) 走真适配器（不要绕开它 —— 要验的正是它的 quta/限额/错误码行为）
# 3) 同一素材再跑一遍 vad 关（判「滤空」还是「真无内容」）
```

- 现成脚本：技能 `local-asr-transcription` 的 `scripts/asr_media_probe.py`
  （A/B 跑 vad 开/关，打印段数、耗时、前几段文本，并对账容器时长 vs 音频流时长）。
- **容器自报时长可能偏小**（本次 60.9s vs 实际 74.5s）→ 超时/限额预算按**音频流**算。
- 真素材跑出的耗时也是环境结论的判据：本次 GPU fp16 转 74.5s 音频含加载 **10.5s**，
  CPU int8 反而 **6.1s**（6GB 卡上 medium 的 CPU 路径实测不比 GPU 慢）→ 别假设「GPU 一定快」，先 A/B。
- ASR 侧的语义/规范化细则见技能 `local-asr-transcription`；Windows 缺 `cublas64_12.dll` 的修复见
  `windows-hermes` → `references/windows-gpu-cuda-dlls.md`。
