# 卡片体量预算、超限拆卡、以及"只搬不改"审计

来源：爆款心法项目卡04 实战（2026-09-16）：双卡 38,091 字符 = 预算 2.7 倍 → 拆成 04a/04b 两套卡。

## 1. 体量预算（出卡端）

- 执行卡 ≤8,000 字符、测试卡 ≤6,000 字符、**每套卡合计 ≤14,000**。
- 判定口径是**每套卡各自**，不是全局合计——所以拆卡是达标的正当手段。
- **越限的先兆**：契约项（端口 + DTO + Settings 键）≥5、GWT ≥20 的卡几乎必然超限。出卡派题时就应该预算好批次，而不是等回炉。

## 2. 超限拆卡的标准动作

1. 按**已批准的批次**拆（不要临时发明切分方式）：如 `04a 身份与凭证 / 04b 计量与策略`。
2. 每套卡**七节齐全**、各自 ≤14,000；卡头写 `parent_card:`、`batch:`、`closure_boundary:`（**子批完成 ≠ 父卡关闭**，统一关闭标准仍按 GWT 全集 + 最终回归 + PERF）。
3. 父卡保留为「总契约与统一关闭依据」，status 改为「已拆为 04a/04b 两套卡」。
4. 压缩手段**只允许**三种：①去掉与本批无关的内容；②用「见 `<文件>` §x」引用替代成段复制架构/模块文档章节与整表；③精简重复的输入清单与口号式表述。
5. **绝不允许**动这些：枚举值 / 字段名 / 错误码 / 表物理名 / 阈值（如`m=65536KiB,t=3,p=4,hash_len=32,salt_len=16`）/ GWT 编号（含 `01A`/`01B` 阶段标记）/ 测试函数名。
6. 压不下去（保全部契约仍超限）→ **如实报告超出的字符数与原因**，不许偷偷裁剪。

## 3. 拆卡验收：「只搬不改」集合比对（必须做，工人自报不可信）

```python
names = lambda t: set(re.findall(r'\b(test_[a-z0-9_]+)', t))
pn, an, bn = names(parent_test), names(child_a_test), names(child_b_test)
assert pn - (an | bn) == set()   # 父卡有、子卡缺 → 有断言被丢掉
assert (an | bn) - pn == set()   # 子卡凭空多出 → 有自造内容
```

实测卡04：父卡 39 个具名标识 = 04a 的 17 ∪ 04b 的 25，零缺零多；去重后主函数仍 24 个（`01A`/`01B` 共用同一主函数），PERF 仍 1 个。数字对不上就是拆坏了。

## 4. 审计正则的容错坑（我误报过两次）

| 误报 | 原因 | 正确做法 |
|---|---|---|
| 报「Argon2 参数丢失」 | 卡面用紧凑写法 `m=65536KiB,t=3,p=4`，而脚本搜 `time_cost` | 搜**值**（`65536`）而非长参数名；或按「关键数值存在」判 |
| 报「GWT 丢失」 | 子卡 §3 用**表格**列 GWT，没有 `### GWT-xx` 标题 | 先 grep 该节的真实排版，再写解析 |
| 报「P-01～P-06 未决残留」 | 卡面写的是「P-01～P-06 **均已冻结**」——引用已决项 | 命中后**必须看上下文**，区分"引用已决"与"待批准" |

通用原则：脚本只做**集合与计数**这类硬判定；语义判定（是引用还是残留、是压缩还是遗漏）先看上下文再下结论。

## 5. 分批覆盖率口径（容易误判成失败）

- 包级 `--cov=<包> --cov-fail-under=80` 在**只跑本批测试**时必然虚低（实测卡04a 为 72.75%，因为旧仓储模块进了分母）。
- 判据：**本批改动模块逐模块**达标（基础层 ≥90%、服务/业务层 ≥80%）即算通过；**包级与"整体不稀释"留给父卡最终统一重跑**（全测试目录一起跑）判定。
- 禁令：不得用 `omit`/`no-cover` 规避，也不得为抬包级数字去扩大测试范围或改动旧模块。覆盖率命令写成逐模块形式（`--cov=app.domain --cov=app.repositories.identity …`）。

## 6. 统计口径也要写清（避免自造）

派生指标（如「主函数数」「映射条数」「截断名条数」「新增/变更/删除名条数」）必须在卡面或裁决里给出**计数口径**（例：11 项 = 9 DTO + 2 枚举，按冻结表逐名计；截断名 7→8 条）。口径缺失时工人只能二选一，实测就出现过「裁决写 10 个、表里实际 11 项」的分歧——发现后由 Hermes 统一改口径并留痕，不要让工人猜。

## 7. 卡面字数口径＝**字符数，不是字节数**（2026-09-25 踩坑）

本项目规则写的是"执行卡 ≤8,000 **字符**、测试卡 ≤6,000、合计 ≤14,000"。**误区**：用 `wc -c` 量——它是**字节**，中文 UTF-8 下约为字符数的 **1.4~1.5 倍**，于是会把完全合规的卡误判为超限并白派一轮"压回"（实测：卡19 任务卡 8000 字节 = **5502 字符**；卡18 任务卡 11299 字节 = 7998 字符）。

- 正确量法：`python -c "import pathlib,sys;print(len(pathlib.Path(sys.argv[1]).read_text(encoding='utf-8')))" <卡文件>`（或任何按字符计数的工具）。
- 派"压回轮"前先按**字符**核对；确认超限再派，并记住中文密度（粗略：字节 ≈ 字符 × 1.45）。
- 复核别人的字数时同样用字符口径，别拿 `wc -c` 与人理论。
