# 错误码面：领域码冻结，表现层问题用「API 层表现码」（用户三次拍板，2026-09-18/19）

## 用户的原则（请当硬规矩用）

**归因必须诚实。** 请求体不合法、服务端内部异常这类**表现层问题**，**不得**复用领域状态码去报，
否则监控会追错方向 —— 用户对此的原始抱怨是：`asr_unavailable` 掩盖了"素材无语音"，
以及"偶发 500 显示成 `analysis_persistence_failed`"。

同时：**04～N 已冻结的 `DomainError` 领域码集合不许扩充**。两者兼顾的做法 = **API 层表现码**。

## 已定案的三个表现码（本项目现状，可作范例）

| 场景 | 状态 | 码 | 性质 |
|---|---|---|---|
| 未预期异常 | **500** | `internal_error` | API 层表现码；`details` 仅 `request_id`，禁回显异常原文/类型/SQL/路径/traceback |
| review 端点请求体不合法（注入 `reviewer_id` 等多余字段）| **422** | `invalid_review_request` | API 层表现码；`candidate_not_reviewable` 仍是领域码 → 409 |
| auth 端点请求体不合法（缺字段/坏 JSON/类型错）| **422** | `invalid_auth_request` | API 层表现码；`invalid_credentials` 仍是领域码 → 401（凭据错误）|

固定口径：**请求体不合法 ≠ 领域状态不对 ≠ 凭据不对** —— 三者分开给码。

## 初审必查的两种「映射表自相矛盾」（本次实测抓到）

1. **同一语义被指到两种状态**：映射表里 `candidate_not_reviewable` 属 **409**，
   但另一段"请求解析错误归属"又把它指给 review 端点 → 实测返回 409，而卡面 GWT 要求 **422**，
   工人三轮都在这个矛盾里打转。
2. **把"请求解析错误"指给领域状态码**：语义错位（Pydantic 拒绝多余字段 ≠ 候选不可审）。

**动作**：出卡端的映射表必须逐码交叉核对（含"解析错误归属"那句）；初审时把 **GWT 里的期望状态**
与**映射表**逐条对齐；对不上的**不要擅自改**，给用户 2–3 个选项（含"新增 API 层表现码"方案）让他拍板，
并把决定写进 `project/decisions/decision_<卡>_<主题>.md`，同步裁决表 + 任务卡 + 测试卡。

## 落地前先做的一次廉价检查

`grep -rn "allowed_codes\|ALLOWED_CODES\|error_codes\b\|允许错误码" tests/ app/`
- **无命中** → 新增表现码不触发任何冻结契约联动，零风险，可直接改；
- **有命中** → 属"联动冻结测试"，按既有规矩**只增不减 + 同步总数**处理。

## 时序管理（避免打断在跑的工人）

若工人**正按旧口径**跑（例如已要求它断言 `invalid_credentials → 401`），**不要打断**：
另写一张**小派工单**（"只改 <该端点> 的请求校验映射 + 对应断言，其余端点不动"）承接，
红线写「凭据错误仍 401 / 其余端点映射一条不许放宽 / 不得新增领域码」。
本次即用 `R09派工单待发.md` 承接，成本远低于重跑一轮。
