# 撞额度 / 被掐断时的「白跑」风险分级（2026-09-17 用户提问后的实测结论）

配套 `SKILL.md` §三「失败模式：先看磁盘，再决定重跑」与
`references/worker-interruption-and-recovery.md`（探针、半成品协议、日志反解）。
本文只回答一个反复被问到的问题：**这一轮会不会白烧？**

## 判据表（按任务类型，不按 token 数）

| 任务类型 | 撞限/被 SIGTERM 时 | 依据（本机实测） |
|---|---|---|
| **出卡 / 裁决类**（先长时间推理，最后才落笔写文件） | ❌ **可能全丢** | 卡08 出卡首轮撞限：烧 82,395 token、磁盘 **0 文件** |
| **执行 / 返工 / 收尾类**（一上来就改文件） | ✅ 基本不丢 | 落盘是**实时**的，不是退出时才写；卡08 裁决进程被 SIGTERM 时，23KB 正文已完整在盘上 |
| `-o` 摘要日志（`*_日志.md`） | ⚠️ **会丢** | 只在**正常退出**时才写 —— 但它只是汇报，**不是产物** |

**一句话**：撞额度 = 丢掉「**还没开始写的那部分**」，不是全丢；先长考后落笔的活风险最高。

## 处置顺序（禁止盲目重派）

1. 扫工作区：`git status --short` + `ls` 目标输出目录 → 确认哪些产物已落盘
2. 扫会话：`ls -t ~/.codex/sessions/YYYY/MM/DD/*.jsonl | head` → 找本次会话，
   `FileChange` 载荷里有**完整正文**（见 `references/worker-interruption-and-recovery.md` §5 与
   `scripts/recover_codex_agent_files.py`）
3. 按「丢失量级」分岔：产出完整 → 只补缺口/补记录，**不重做**；真全丢（出卡类）→ 先探额度再重派
4. 需要重排时的优先级：**执行/返工类 > 出卡/裁决类**（前者中断损失小，后者一旦中断全丢）

## 汇报口径

用户问「撞额度会不会白跑」时，直接给上面这张表 + 本轮的实测数字（烧了多少 token、盘上有多少文件），
比「可能会白跑」这种模糊回答有用得多。这条口径来自用户 2026-09-17 的原话追问。
