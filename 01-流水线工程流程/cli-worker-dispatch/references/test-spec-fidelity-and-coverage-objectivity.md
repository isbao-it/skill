# 自报「已实现 N 组」不可信 + 覆盖率客观化 + 回查老账（2026-09-18/19 实卡审计）

来源：卡12（FastAPI 接口层）的 R01→R07 全过程，以及由此触发的对已合入 18 张卡的复核。

## 1. 症状：组名让人以为做了，真实调用面很小

工人连续三轮（R01/R02/R03）交回「按 TDD 新增固定 8 组 API 测试，**16 passed 全绿**」，
实际 `tests/api/` 只有 **394 行 / 9 个函数 / 12 次真实 HTTP 调用**，其中：

- `test_12_04`（202/jobs）、`test_12_05`（幂等）、`test_12_08`（分层守卫）**零次 HTTP 调用** —— 直接调仓储纯函数或假门面；
- `test_12_06`（业务路由）只冒烟 1 条路由，而卡面要求 **35 条每路由至少冒烟**；
- `test_12_07`（错误码）只触发 **1 个**错误码，卡面要求「§3 逐码参数化」。

**用例名的 `test_12_04_...` 前缀制造了"那一组做了"的错觉** —— 这是最危险的形态。

## 2. 验收必须做的四个硬动作（缺一条就可能放过放水）

1. **断言 → 用例逐条映射**：把卡面 §4 的**每一条**要求（每条路由、每个错误码、每个授权矩阵格、每个边界值）
   映射到一个真实用例名；**映射不上的即缺失，直接判 `blocked`**。永远不接受"已实现 8 组"这类自报。
2. **统计真实调用面**（一条命令定性）：
   ```bash
   grep -cE 'client\.(get|post|put|delete|patch)\(' tests/<dir>/*.py
   ```
   组数 8 却只有十几次 HTTP 调用 → 不合格；**某个"路由/幂等"类测试文件 0 次 HTTP 调用 = 放水**。
3. **覆盖率口径客观化**：
   - 用**整文件**百分比对照门槛；**新建文件没有"历史行"可豁免**——对本卡新建的文件，整文件≈增量；
   - 「本卡新增/变更语句」口径只允许用在**既有大文件**上，且必须给「变更语句清单 ∩ missing」的计算过程；
   - 工人若用「不以已存在大文件的全量覆盖率替代本卡门槛」来申辩，**先看该文件 `git status`**：
     若是本卡新建（`??`），这句申辩不成立。
4. **假替身红线**：只有"证明 0 调用"可以用 spy/假门面；
   **授权判定、持久化、状态机、幂等回放必须真 SQLite + 真服务**（假替身顶掉持久化 = 门槛虚设）。

## 3. 回查已合入卡的老账（一次性做，性价比极高）

四把**互相独立**的尺子：

| 尺子 | 命令/做法 | 能抓到什么 |
|---|---|---|
| ① 全量单次覆盖率 | `pytest tests/ -q --cov=app --cov-report=term-missing` | 哪个模块整体偏低 |
| ② 生产类是否被测试提及 | `grep -rn "<ClassName>" tests/` **零命中 = 0 覆盖** | 整类从未被测（实测抓到 `AnalysisRepository` 约 313 行真 SQLite） |
| ③ 卡的 `--cov` 目标 vs 卡写入的模块 | 逐卡比对测试卡 §3 命令与 `git show` 该卡改动 | 门槛漏模块（卡08 的根因：`app/repositories/cases.py` 不在 `--cov` 目标里） |
| ④ 是否真走 SQLite | `grep -c "MagicMock\|Fake"` 对比真连接 | 端到端测试全挂在假替身上 |

**结论口径**：多数情况根因是**卡面的覆盖率目标漏了模块**（出卡/初审的责任），不是工人放水 →
处置是**新出一张"只补测试不改实现"的卡**（如 `卡08b`），并在卡面把 `--cov` 目标补全。

## 5. 派工单的约束必须与**项目自身既有约定**一致（2026-09-19 卡08b 实测，白烧一轮 84k）

给补测卡写"**夹具走真实生产路径生成**（真实 `save_*`）**禁直插 ORM 行**"时，先确认两件事：
① 那些实体**在项目里真的有生产写入 API** 吗？② 同胞测试**实际怎么造数**？

实测反例：派工单要求用生产 `save_*` 建「字幕片段/评论/心理词/分类」，但项目里**根本没有这些写入 API**，
而**同胞集成测试一律用既有夹具** `RepositoryRows.insert(<table>, **values)`（`tests/integration/repositories/conftest.py`）。
工人读完发现**按约束无法完成、按白名单又查不到别处** → 只能停报索取，白烧一轮。

**正确写法**：把约束分成两层 ——
- **被验证的写入路径**必须是生产仓储方法（这是卡的目的）；
- **种子数据**用项目既有的造数夹具（并在派工单里**点名它**：文件 + 类 + 行号），
  同时明确"**禁**的是生产代码里直插 ORM 与手搓持久化 JSON，**不是**禁测试造种子"。

**集成测试类补测卡必列的读取面**：`tests/integration/**/conftest.py`（夹具与造数助手）、
**同胞 `test_*.py` 体例样板**（尤其同目录最接近的那个）、`tests/conftest.py`、
`app/repositories/*.py`（局部读：先 grep `^class `/`    def ` 定位）。

## 7. 模型分档（2026-09-18 定，2026-09-25 更新到 6 代，别自行升降档）

- 默认 `gpt-6-sol`（+ `model_reasoning_effort="high"` 出卡/架构；`medium` 用于中等卡与机械修复）；
- 低档 `gpt-6-luna`（`low`：文档同步、格式、探活）；`gpt-6-terra` **不可用**（400）；
- **sol 通吃高/中两档**（用户原话「高用 6sol 最高，中的话就用 6sol 的中」），**别自行把中档降级到 luna**；
- `gpt-6-astra` **仅用户点名时使用**（难卡会被点名；astra 烧额度明显更快，用过即回落到 sol）。
- **CLI 升级后必须重新探活模型名再改分档**：用户曾纠正「怎么又用 5.6sol…你的派卡没更新」。
