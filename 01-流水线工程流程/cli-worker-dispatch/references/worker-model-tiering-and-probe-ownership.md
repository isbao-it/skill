## 一、档位（用户原话整理）

> 「以后派卡片如果是难度高的用 gpt5.6sol，写代码也用 sol，如果是简单任务用 terra，如果是一些
> 最简单的像是 deepseekv4.1flash 级别的用 5.6luna。gpt6 除非我叫你否则不要用」
> —— 2026-09-18
> 补充澄清（同场）：「写代码则和出卡用同模型」

| 卡的性质 | 模型 | 判据 |
|---|---|---|
| 难卡（出卡 / 架构 / 跨卡裁决 / 复杂失败诊断） | **`gpt-6.1-sol`** + **`medium`** | 架构设计、技术选型、新栈首次落地、并发/安全边界、状态机、复杂调试。**2026-09-27 起用 6.1 代替换 `gpt-6-sol`**；实测需 **codex CLI ≥ 0.160.1**（0.157.0 下报 400 `model is not supported when using Codex with a ChatGPT account`，且提示 `Model metadata not found`） |
| 卡面修订 / 微修（已定位到行） | **`gpt-6-luna`** + `medium` | 按**已定位到行**的结论替换文案/字段/签名 —— 是替换不是判断，**禁 sol**（2026-10-08：一度按“与卡面同族”给了 sol，属错配） |
| **模块文档 / 错误码表 / 文案同步 / 派题回执** | **`gpt-6-luna`** + `medium`（纯格式 `low`） | **禁 sol**：这类是“按已定稿文档做提取与逐字裁剪”，不产出判断。2026-10-08 实测：误用 sol 跑 2 轮 = 白烧 4 个 5h 配额点 |
| **执行写码** | **`gpt-6-luna`** + `medium` | **用户 2026-09-26 再次强调：写码一律 luna，禁 sol（额度烧太快）**；配套硬要求：**在出卡阶段就把卡切成 luna 能吃的小片**（一个目标、少量文件、可独立真跑）。实测教训：一张大卡被 luna 连续 6 轮空转、改升 sol 救火 → 总账比"一开始切小"贵得多 |
| 最简 / 纯文书（低） | `gpt-6-luna` + `low` | 格式整理、措辞修订、文档同步、探活 |
| `gpt-6-astra` | **禁用**，除非用户当次点名 | 高档模型，用户明确控成本 |

> **档位表 2026-09-26 定稿（CLI 0.157.0 实测）；2026-10-08 按配额实测修订**：`gpt-6-sol`/`gpt-6-luna` 可用，`gpt-6-terra` 报 400。
> **2026-10-08 新增两条口径（实测）**：
> ① **配额按「档位 + effort」烧，不按 input 大小** —— `sol`+`high` 9 个用量事件 = 5h 窗口 **+5 点**；`luna` 122 个事件 / 544 万 input = **+5 点**（差约 10 倍）。所以「省额度」的第一手段是**别把非判断类活派给 sol**，第二是**合并轮次**（每轮约 21.5k 底噪 + one-shot 溢价）。
> ② **凡要 `high` 的派题必须写明“为什么需要 high”**；写不出就默认 `medium`。同理，凡派 sol 的轮次要能一句话说清“这轮产出的是判断还是提取”。
> 用户原话：「**额度消耗有点快写代码还是用 6luna**」——所以**执行工人一律 luna**，配套要求：卡要切小、派工单只给该片所需段落、每片可独立真跑。
> 教训：CLI 升级后**必须复探模型名与档位**；也别自行把写码档升到 sol（用户按额度拍板）。

要点：

### 协调者角色（2026-09-26 用户拍板）
- **谁协调要看额度归属**：拆片/写派工单/盯片/合并复验本来由 Hermes 做，**不消耗 Codex 额度**；派 Codex 工人协调是**把活搬进稀缺额度池**，不是省。用户明确接受这个取舍时才派。
- 若派协调者：`gpt-6-sol` + `low` 够用（协调=约束下的摘要+接口判断，非深推理），职责=拆片/写**窄**派工单/启动各片/片间只读复核/写汇总。
- **接口冻结别用 low**：签名错一个，所有并发片全废 → 冻结轮用 `sol`+`medium`，且用冻结计数测试把住。
- **不推荐嵌套派工**：验证负担不转移、嵌套会话难追溯，且协调者为派工需重读卡面+架构，多烧的额度正好抵消想省的。
- 并发三条件仍成立：写文件集合不重叠 / 不碰共享冻结资源（同一文件或同一冻结断言=串行）/ 依赖已就绪（**先冻结接口再并发**）。

- **档位单位 = 卡的类型，不是环节** —— 但**出卡与写码可以不同档**（2026-09-26 修正，覆盖早前
  「写代码则和出卡用同模型」的旧口径）：出卡/架构/裁决用 `sol`+**`medium`**（要 high 须写明理由），**执行写码与文书类（模块文档/文案同步/微修）用 `luna`**（用户按额度拍板；2026-10-08 修订，原为 sol+high）。
  唯一硬约束：**同一张卡的写码必须同一档**，别在一张卡内部再按文件分模型。
- 判据是**卡的性质**（推理深度、错误代价、上下文体积），不是"谁在写"。
- 派工单顶部写清：模型名 + 一句"本片为何归这档" + 修订记录（旧值 → 新值 + 依据）。

### 本机模型名的发现方法（只用来看"存在性"，不代表档位）

`~/.codex/models_cache.json` 里可以枚举出本机 codex 认识的模型 id：

```bash
python -c "
import json,io
d=json.load(io.open(r'C:/Users/<user>/.codex/models_cache.json',encoding='utf-8'))
out=set()
def walk(o):
    if isinstance(o,dict):
        for k,v in o.items():
            if k in ('id','slug','model','name') and isinstance(v,str) and ('gpt' in v or 'codex' in v): out.add(v)
            walk(v)
    elif isinstance(o,list):
        for i in o: walk(i)
walk(d)
print('\n'.join(sorted(out)))
"
```

2026-09-18 实测该清单为：`codex-auto-review / gpt-5.5 / gpt-5.6-luna / gpt-5.6-sol /
gpt-5.6-terra / gpt-6-astra / gpt-reserve`。**清单只说明"这个名字存在"，不说明档位高低，更不是
用户认的分档** —— 分档永远以本文件第一节 / 用户当次指令为准。

## 二、额度探活：归用户，调用方不要再自己探

用户 2026-09-18 原话：「探测额度你以后不用搞了这个交给我」。

- 这条**覆盖**了 `references/quota-probe-and-caller-economy.md` 第一节「派大活之前先探活」的
  无条件做法 —— 现在**不要自动探活**，配额状态从用户那里取，或按用户当次指令办事。
- 探活并不便宜：一次 `codex exec -m <模型> ... "只回复两个字：正常"` 要注入项目规则 + 仓库上下文 +
  工具定义，实测 **23,349 token**（另一次用高级模型探活实测 **24,607 token**）。见
  `references/quota-probe-and-caller-economy-2026-09-18.md`。
- 挂钩 cron 自动续跑时同理：探针加不加、用哪个模型探，**先问用户**，不要替用户判断配额。

## 三、踩坑记录：照抄文档里的「用户定案」

**发生了什么**：某技能里写着

> ⚠️ 模型（2026-09-16 用户定，已调整过多次，以此为准）：默认一律 `-m gpt-6-astra`（出卡/架构 +
> 写代码都用它）；用户明说省额度时才临时切 `-m gpt-5.6-sol`。不要在 Hermes 侧自行分角色改模型
> （已被纠正三次）。

我把它当作用户定案转述（原话"你 2026-09-16 已定过，而且我因为自作主张分模型被你纠正过三次"），
据此把派工单的模型行从 `gpt-5.6-sol` 改成 `gpt-6-astra` 并**真的派了工**。用户立刻反问
「我什么时候说过用gpt6」，并说明真实档位是 sol / terra / luna、`gpt-6-astra` 除非点名否则不用。

同一轮还叠加了第二个错：用 `gpt-6-astra` 去做额度探活，白烧 **24,607 token**。

**教训（两条，都要写进习惯）**：

1. **文档里写的"用户定案"不是证据。** 日期、"已调整过多次"、"已被纠正过 N 次"这类措辞会让人
   产生"这条已经确认过了"的错觉，恰恰最该核实。凡涉及**模型名 / 档位 / 策略 / 权限范围**的定案，
   用之前当次向用户核实一句，成本一分钟。
2. **发现文档与用户当次说法冲突时，先停下报告，不要"按文档执行 + 事后说明"。** 当时更省事的做法是
   直接问一句"派工单里写的是 X，你说的档位我记的是 Y，用哪个"，而不是先派出去再解释。
3. 传给用户的账要算清楚：错了就明说错在哪、烧了多少、怎么纠正的，不要含糊过去。

## 四、被中断的派工再派时的检查

杀掉一个 `codex exec` 之后要确认没有孤儿进程再重派（否则新会话可能在工具握手阶段自停、
一个文件都不写）。**只按确认的 PID 定点杀，禁止按名字模式批量杀** —— 本机曾把当时仍在跑的另一个
worker 一起杀掉。认人的只读清单脚本见 `references/worker-process-hygiene.md`；
在 Windows 上写这类清单脚本有个坑：**内联 PowerShell 转义会炸**，见 `windows-hermes` skill。
