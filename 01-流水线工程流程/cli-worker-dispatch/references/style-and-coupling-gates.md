# 风格一致与高内聚低耦合：出卡/派工/验收三道闸（2026-09-20 用户要求）

> 用户原话：「**代码风格要一致，别到时候不一样就乱了，还要保持高内聚低耦合**」。
> 单人长期维护的项目里，风格漂移与结构失控比"少写个功能"贵得多。所以这不是"建议"，是**可核查的打回项**。

## 1. 出卡端（架构师）必须写进双卡 §硬边界
1. **风格照抄既有**：点名 1～2 个**同层同类既有文件**作为风格参照（例如"照 `app/services/auth.py` 的写法"），
   比抽象地写"保持风格一致"有效得多。
2. **逻辑放对层**：业务规则 → `app/services/*`；SQL → `app/repositories/*`；HTTP 层只做参数与映射；
   `app/api/*` 禁 import `app.repositories`/`app.db`/`sqlalchemy`（分层守卫测试会抓）。
3. **复用不复制**：列出本卡**必须复用**的既有能力（哈希/限速/时钟/错误信封/鉴权主体/事务作用域），
   并**禁止**为本卡另写同类实现（这是"低耦合"最容易破的地方）。
4. **不造新抽象**：除卡面明确要求，禁新增端口/协议/工厂/中间层/新文件。
5. **改动最小必要**：只碰卡面列入的文件；禁重命名既有符号、禁顺手格式化无关代码。
6. **偏离须停下报告**：认为必须偏离既有风格或新增抽象层时，工人要停下说明，不许自行决定。

## 2. 派工端（调用方）
- 派工单硬边界里加一条**风格条款**（照上面的 1～6 压缩成 2～3 行）；常驻纪律已含该节的（如本项目
  `~/.dsh-worker/AGENTS.md` 与项目 `AGENTS.md`）只需一句"按常驻纪律 §代码风格与结构纪律"。
- 要求工人在 `结论.md` 自报三件事：**新增逻辑落在哪一层**、**复用了哪些既有能力**、**风格参照了哪个文件**。

## 3. 验收端（调用方，这里是真正兜底的地方）
1. **分层**：跑既有分层守卫测试（如 `tests/api/test_12_08_layering*`）；再 `grep -n "^from app\.\|^import " <新增/改动文件>` 人工扫一遍。
2. **复制粘贴检测**（低成本高收益）：
   - 对工人新增的核心逻辑，`grep -rn "<关键函数名/关键 SQL 片段>" app/` 看是否存在等价实现；
   - 特别查：是否又写了一个哈希/限速/时钟/错误映射（这类最容易重复造）。
3. **风格抽查**：抽 2～3 个新增函数，与同层既有函数对照：命名、docstring 格式、注释"为什么"、类型标注、异常处理风格。
4. **抽象层审计**：`git status` 里**新增的文件**是否都在卡面白名单；新增的类/协议是否有必要。
5. **改动面审计**：是否出现与本卡无关的改动（重命名、格式化、注释重排）——发现即判 `blocked`，不"顺手接受"。
6. 判据写死进验收报告：`风格一致 = 是/否（附 1 条证据）`、`新抽象层 = 无/有（必要性说明）`、`跨层依赖 = 无/有`、`重复实现 = 无/有`。

## 4. 反例（本项目真实发生过的形态，验收时重点看）
- 把业务规则写进路由处理器（`app/api/routes.py` 里出现哈希、状态机、事务）；
- 为一张卡另写一套"简化版"限速/时钟/错误映射，而不是复用既有端口；
- 新增一个"以后可能用得上"的中间层或工厂；
- 为新卡新建一个与既有仓储并行的仓储类，导致同类 SQL 两处维护；
- 顺手重排/格式化了无关文件（git diff 里出现本卡不该碰的行）。
