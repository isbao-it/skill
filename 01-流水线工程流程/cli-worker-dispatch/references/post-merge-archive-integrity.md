## 1. 用 mv 归档交付物后，v2 产出里的引用**必然失效**

**背景**：项目约定 `待审核/<NN>/` 只放「已交回但未合入」的产物，合入时用 **mv**（不用 copy，避免影子副本）
迁到 `project/outputs/<NN>/`。但 v2 产出（`summary.json` / `acceptance.json`）里存的是**指向彼此的相对路径**，
其中 `acceptance.json` 还带**被引用文件的 SHA-256**。一 mv 就全断。

**症状**：校验器（`project/templates/validate_summary.py`）报引用路径不存在；或改了正文后报 hash 不符。

**三步修法（缺一不可）**：

1. **改路径 + 重算 sha256**：用 Python 读 JSON → 把指向旧路径的字段（如 `origin.derived_from`、
   `worker_summary.path`）改写为新路径 → 若被引用文件内容也变了，**重算 `sha256` 覆盖旧值**
   （只改路径不动内容时 hash 不变；动了内容不重算必报 hash 不符）；写回时用 `newline='\n'` 避免 CRLF 翻转。
2. **重跑校验器**：`.venv/Scripts/python.exe project/templates/validate_summary.py <文件>`，
   必须 `0 ERROR 0 WARN`（实测修复后 PASS）。
3. **旧路径的删除要单独 staging**：`git add project/outputs/<NN>`（新位置）**不会**记录旧位置的删除 ——
   需要再跑一次 `git add -A project/outputs/待审核`。漏掉会怎样：`git status` 长期挂着两条 ` D`，
   看起来像未完成的改动。**mv 类操作后永远检查 `git status` 有无残留 ` D` 行。**

**顺带**：归档后核一次 `待审核/` 清单，确认只剩 README 与并行线未归档件；空目录记得 `rmdir`。

## 2. `-o` 文件不是进度指示器（codex 后台任务）

**误判场景（用户原话「你看下怎么没反应了」）**：派了后台 codex 任务，`-o <日志>.md` 一直 0 字节，
看着像卡死/失败，实际上工人正在正常干活。

**原因**：`codex exec -o <文件>` 只在**进程退出时**写入最终答复。跑到一半 `-o` 必然为空。

**正确判读顺序**：

| 看什么 | 含义 |
|---|---|
| **重定向的运行日志**（`> <name>_运行.log 2>&1`）体积是否在增长 | 增长的才是真实过程（实测跑到 285KB / 490KB） |
| 运行日志尾部有无 `EXIT=0` / `XXX_EXIT=$?` 标记 | 有标记 = 该段已结束（串行链式任务用 `;` 串起来时尤其重要） |
| 产出/交付文件是否出现在磁盘 | 最硬的证据 |
| `-o` 文件字节数 | **最弱的信号，别用它判断死活** |

**纪律**：不要因为 `-o` 为空就重派 —— 同一个账号双开很容易再撞额度上限，
且会出现两个进程写同一仓库的局面。串行链式（`cmd1; cmd2`）本身就是为了守「同账号同时只跑 1 个主动任务」。

## 3. 拆卡时的目录约定（避免工人误删草稿）

拆批卡（如 07 → 07a/07b，先例 03a/03b、04a/04b）时：**为拆出的批次新建独立目录**
`project/cards/<NN>a/` 放新的双卡，**父目录 `<NN>/` 的原始草稿原样保留**。

- 工人只被授权**新建**拆批目录下的文件；**禁止**删除/改名父目录草稿（写进派工单硬禁止段）。
- 父目录草稿的去留由 Hermes 在合入时决定并单独说明（默认保留，作为设计演进留痕）。
