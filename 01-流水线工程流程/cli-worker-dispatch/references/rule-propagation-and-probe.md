# 规则落地与探针验证（2026-09-15 实测教训）

> 来源：一次真实的"改了规则但没生效"事故。流水线侧把额度/体积纪律写进了自己的文档体系，
> 连跑 4 张卡**行为毫无变化**；直到把同一段纪律同步进**工人真正读的文件**才见效。
> 本文记录"纪律从哪到哪才算生效"，以及验证它生效的低成本探针。

## 一、核心事实：工人只读「它自己的规则文件」

CLI 工人启动时加载的规则文件是固定三处（各家 CLI 等价）：

| 工人 | 全局 | 项目级 |
|---|---|---|
| Codex CLI | `~/.codex/AGENTS.md` | `<项目>/AGENTS.md` |
| Claude Code | `~/.claude/CLAUDE.md` | `<项目>/CLAUDE.md` |
| opencode 等 | 见各自文档 | 同上模式 |

**写在别处的纪律对工人不可见** —— 包括：知识库/vault 文档、流水线权威原文、模板目录、
agent 自己的 skill、飞书/微信笔记。派工指令里的约束只是**一次性补丁**，下一个人派工就失效。

推断链上最容易错的一环：以为"我改了权威原文/模板，出卡的人自然会照做"。
**不会。** 出卡/派工也是由某个 agent 会话执行的，它同样只读上面那三处。

## 二、实测对照（同一套纪律，接线前 vs 接线后）

| 阶段 | 动作 | 结果 |
|---|---|---|
| 接线前 | 纪律只写进项目外的流水线文档 | 连跑 4 张卡：轮数 **91 / 126 / 88 / 112**，产物体积 40k / 40k / 10k / 10k 字符 → **毫无变化**，其中一张还撞了额度上限 |
| 接线后 | 同段纪律同步进 `~/.codex/AGENTS.md` + `~/.claude/CLAUDE.md` + 项目 `AGENTS.md` | 产物体积**首次达标**（9,942 / 10,276 / 13,143 ≤ 14,000 字符），并出现 **26 轮 / 235 万 input** 的轻量卡 |

注意：接线后仍有大卡（88–112 轮）——**任务本身复杂度是主因**，规则只能消除"本可避免的浪费"。
不要用单张卡的结果反推规则效用（见第五节 归因诚实）。

## 三、接线怎么接（可复用步骤）

1. **两端都要写，缺一不可**
   - **执行端**：读取白名单、输出重定向、轮数预警线、验证分工（谁跑全量回归）
   - **出卡/委派端**：产物体积上限、行为组上限、禁成段复制、关键常量必须钉死
   - 只写执行端 → 下一张卡依然肥；只写出卡端 → 工人照样读全仓、贴全量输出
2. **全局两处同源**：用**同一段字符串**写进 `~/.codex/AGENTS.md` 与 `~/.claude/CLAUDE.md`，
   写完用 sha256 校验同源（改一处必须同步另一处，否则两个工人行为不一致）
3. **项目级只写增量**：项目 `AGENTS.md` 只补项目特有项（产出目录、公共规则文件单列、白名单口径），
   并**指回全局**，避免同一段规则四处漂移
4. **改前留退路**：把原文件 `copy2` 到 temp 作回滚点（非 git 目录没有别的退路）
5. **保持原行尾**：`open(p,'rb')` 读 → 记 `b'\r\n' in raw` → 解码编辑 → 按记录的行尾写回 → 二进制写。
   用 patch 类工具会把 LF 文件写成 CRLF，产生整文件 diff 噪音
6. **别写长**：规则文件越长遵守率越低；新增段落控制在十几行，只写可检查的规则（"保持高质量"这类不写）

## 四、探针验证：别假定"文件写了就生效"

接线后跑一次**只读探针**，让工人复述规则：

```bash
codex exec -m <模型> -c model_reasoning_effort="low" -c sandbox_mode="read-only" \
  -c approval_policy="never" --skip-git-repo-check \
  "只回答一个问题，不要读任何文件、不要执行命令、不要写任何文件：你当前加载的开发规则里
   「<规则名>」规定的是多少？用一行回答，不要解释。"
```

- 成本约 **2 万 input**（低推理 + 只读 + 单轮），属探针级开销，**别计入任务成本**（见取数口径里的 `probe` 归类）
- 判定：回答**命中规则原文**才算接线成功；答错/回避 → 查路径、文件编码、加载顺序
- 这条探针也适用于"换了工人"（Codex→Claude→opencode）后的资格预检

## 五、归因诚实：别把"这次活小"记成"流程省了"

实测出现过：新流程下某卡 **26 轮 / 235 万 input**，而历史大卡 **98 轮 / 1,299 万**。
看着像 −80%，但两者**任务体量不同**（前者一个模块的行为闭环，后者 15 张表的契约组）。

评估顺序：

1. **先看客观项**：产物体积是否达标（≤上限）、产出格式是否合规（`summary.json` 是否存在）——
   这些与任务大小无关，最能反映规则是否真的生效
2. **再看轮数 / input**：必须注明样本量与任务规模差异
3. **结论门槛**：同类任务 ≥3 张才有"省了 N%"的资格；否则只能说"出现了改善迹象"

## 六、附：校验器要有负向自测

给交付物写格式校验器（如 `summary.json` 的校验脚本）时，**必须造一份故意违规的文件**证明它会报错。
实测负向样本抓出：`status=approved`（工人无权声明批准）、`result=pass` 却 `exit_code=1`、
覆盖率项通过却缺 `coverage_percent`、`change` 用非法词。
没有负向自测的校验器等于没校验 —— 它可能对任何输入都说 PASS。

配套的**来源诚实**约定：工人交 `summary.json`（自报），验收方另交 `acceptance.json`（独立结论），
两者并存不互相覆盖。验收方从旧格式结论反解出的摘要，必须在文件里标 `origin`（谁反解、从哪反解、
"非工人自报"），不要让它看起来像工人自己交的。
