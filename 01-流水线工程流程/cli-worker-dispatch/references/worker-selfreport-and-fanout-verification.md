# 验收侧的两个盲区：工人自报滞后 · 定向绿≠套件绿

来源：2026-09-17 卡06 实测（`cli-worker-dispatch` 的姊妹篇，配合 `references/codex-exec-dispatch-pitfalls.md` 看）。
这两条都是「调用方按工人自报做判断」造成的浪费，只有调用方自己动手才治得好。

## 一、工人自报的状态可能滞后于它最后一次编辑

- **现象**：工人交回时自报「`app/repositories/scoring.py` 覆盖率 47%、Ruff 31 错、最后补强未重跑」。听起来要整轮返工。
- **真相**：它在撞上「工具调用上限」之前**没来得及重测**，自报的是**上一轮**的旧快照。调用方独立复测：覆盖率 **95%**（已达标），Ruff 32 错（真缺口），另外就是缺交付 JSON。
- **铁律**：验收第一步永远是按**当前磁盘快照**自己量 —— 定向 pytest + **逐模块** coverage + ruff，用**自己**的输出决定返工范围，别按自报下结论（自报可能悲观，也可能乐观）。
- **推论**：工人诚实报「未验证 / 撞上限停下」**不是失败**，是熔断生效。处置 = 自己重测 → 派一个小的收尾单（本例：只修 Ruff + 补 `summary.json`，写明 ≤12 次工具调用），而不是重跑整场。

## 二、定向绿 ≠ 套件绿（全量必须由调用方跑）

派题纪律要求工人只跑定向用例（省额度），这带来两个**结构性盲区**，只有调用方跑全量才看得见：

1. **收集期失败**：新测试目录复用既有 basename（如两个 `test_contracts.py`）在 pytest 默认 `prepend` 导入模式下报 `Interrupted: N errors during collection`。定向只选一个目录时不暴露。根治 = `[tool.pytest.ini_options] addopts` 加 `--import-mode=importlib`。
2. **冻结集合契约测试**：新增仓储/服务模块文件必然撞「文件清单 + 方法计数」硬编码的既有契约测试。同类问题已连踩 04a、05、06 三次。

处置：**在派工单里就预授权**只增不改的扩展 ——「若既有测试仅因新增文件/方法而失败（冻结集合类），授权最小扩展：只增条目/计数，**不得删除或放宽任何既有断言**，并在结论中列明；其他既有测试失败必须停下报告」。比验收阶段才发现再返工一轮便宜得多。

验收时注意：计数与 docstring 更新会让 `git diff --numstat` 出现「删除行」——要**逐行看那几行是不是计数/文案更新**，别把正常扩展误判成偷删断言，也别反过来放过真的删断言。

## 三、覆盖率要「逐模块」看，不看总分

总分达标会掩盖单模块不达标。基础层按模块卡 ≥90%（如卡06 的 `services/scoring` 92%、`repositories/scoring` 95%、`domain` 95%），逐模块列出来给用户看，比一个「TOTAL 95%」可信得多。
