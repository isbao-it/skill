## 二、单卡全链路预算（可直接用于排期与"要不要返工"的取舍）

一张 C 类卡（行为组 6–7、白名单 6 文件）走「出卡 → 修订 → 执行」**实测 ≈50 万 token**：

```
出卡 136k~250k  +  范围受限修订 85,790  +  执行 163k  ≈ 400k~500k
                 +（若返工）      84k~99k
```

推论（已在实测中兑现）：

- **一次出到位更省**：出卡阶段多花 3–5 万把设计点问清，便宜于事后再来一轮修订（8.6 万）+ 一轮返工（8–10 万）。
- **「范围受限修订」与「一次返工」同量级（≈8–9 万）** —— 所以用户中途提出的设计质疑，
  走修订会话的成本是可接受的，**不要为了省钱而拒绝改契约、也不要主代理自己动手改设计**。
- 让工人**自跑校验器**、把 schema 枚举写进派单，能省掉一整轮"归一"（那篇 §二已详述，本次已验证首次即合规）。

## 三、「范围受限修订会话」标准姿势（用户质疑设计取舍时）

触发：用户读完裁决/卡面后提出**流程顺序或成本**层面的质疑（实例：「相近词合并应该只在达到高频的
候选里做，而不是每次都合并再选高频，这不更省吗？」）。这类质疑**可能对、也可能踩坑** ——
顺着改可能造出一个**静默缺陷**（召回下降但不报错）。

**四步法**（实测有效）：

1. **先讲目的，再谈顺序**。把"这个步骤存在的首要理由"摆出来。实例：合并的目的就是**把概念频次攒起来**；
   改成"先按表面词筛高频再合并"会让概念频次**碎片化** → 真高频概念出不了候选，**且不报错**。
2. **把成本拆成可判断的几项，用成本结构纠正直觉**。实例：字符串比较（Levenshtein/bigram Jaccard）
   是微秒级、500 词 ≈ 秒级；**真正贵的是 LLM 调用**，而它已被"未决对"门槛过滤 → 现状瓶颈不是用户以为的那部分。
3. **给 2–3 个可选项 + 明确推荐 + 每项代价**（保持原序+加弱下限预筛 / 按原意改序 / 先不改）。
   推荐要落到"最小代价换到用户想要的收益"。
4. **落地走独立的修订会话**（新会话 + 紧派题，≤12 次工具调用），派单里写死三类内容：
   - **把用户直觉的失效边界写成可检查禁令**：新前置条件**必须弱于**最终门槛
     （实例：`surface_document_count>=3 OR surface_active_weeks>=2`；**禁止**用 `active_weeks>=3`
     或 `max(8,P75)` 做预筛）；
   - **零假设式验收对冲**：同一批 golden 样本**前后对照**（`有预筛召回 == 无预筛召回 >= 85%`、
     难负例误合并仍为 0）—— 让"省成本"这一步自己证明**没偷召回**；
   - **边界**：只许改"裁决补丁 + 双卡"，**不许**改架构正文（主代理并入）、不许碰实现代码、不许 git；
     字符上限（任务卡 ≤8,000 / 测试卡 ≤6,000）与**行为组数不变**（把新条件参数化进既有行为组）。

## 四、修订交回后的主代理自检（本次靠脚本抓到走形风险）

用户批准的是**方向**，落到契约文字时最容易走形。交回后**不要通读判断**，直接写断言：

```python
# 三条硬检查（本次实测有效）
assert g_task == 7 and g_test == 7            # 行为组数未变（用 - **09-0\d 计数）
assert 'merge_prefilter' in 任务卡 and 'merge_prefilter' in 测试卡   # 新条件确实进了双卡
assert len(任务卡) <= 8000 and len(测试卡) <= 6000                    # 字符上限仍在
# 语义检查：预筛阈值必须弱于最终门槛（3 OR 2  vs  ≥3 且 ≥max(8,P75)）
```

并入架构时用**程序化抽取**（从裁决/补丁里按标题区间抽正文，不要手打转写），并顺手把被修订的
原句改成「本句经 §X.Y 修订：…」留指针 —— 下一个人读架构时才知道这里有前情。
