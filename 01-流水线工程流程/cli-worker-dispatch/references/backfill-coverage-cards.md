# 「补测卡」规范：给**已合入**代码补测试（2026-09-19 卡08b 实测）

触发场景：审计/全量发现某生产类**从未被 `tests/` import**（0 覆盖），但实现早已合入
→ 只能"**只补测试、不改实现**"。这类卡有三个必须预先写死的口径，否则工人要么判 `blocked`、要么被逼造假红灯。

## 1. 门槛写「被测类区间 statement ≥X%」，**不是整文件**

实例：`app/repositories/cases.py`（248 statement）里既有本卡要测的 `AnalysisRepository`(536–841)，
也有**本卡不测**的 `CaseRepository` / `CaseManagementRepository`。

| 命令 | 整文件 | 被测类区间 |
|---|---|---|
| 只跑新测试文件 | **46%**（怎么补都过不了整文件 90% 门槛 → 白烧一轮） | 100% |
| **联跑整个 `tests/integration/repositories/` 目录** | **90.3%** | **73 statement / 0 缺失 = 100%** |

⇒ 卡面必须**同时**写三件事：
1. 门槛 = 「**被测类 `X`（`file:起止行`）statement ≥90%**」；
2. 覆盖率命令 = **联跑整个测试目录**（否则整文件数字没有意义）；
3. 交付记录**另报整文件百分比**（口径写进 `coverage_scope`）。

判据命令（不用跑测试也能核区间覆盖）：
```bash
python -m pytest <test file> -q --cov=app.repositories.<mod> --cov-report=json:<tmp>.json
# 再读 json：executed_lines ∪ missing_lines ∩ [起,止] → 区间 statement 数；missing ∩ [起,止] → 缺失数
```

## 2. 补测卡**豁免「先红后绿」**

被测实现早已合入 → 行为红灯**不可能也不应伪造**（工人报"首跑 9/9 通过"是正常的，不是放水）。
**替代判据＝覆盖缺口可复现**：补测前 `grep -rn <ClassName> tests/` **零命中**即证明该类 0 覆盖
（把这条命令写进卡面，让工人用证据代替红灯）。

不写这条的后果：工人为了凑"红灯"去改无关断言，或老实报 `blocked` 让整轮白跑。

## 3. 种子数据用**项目既有夹具**，不要逼它走不存在的生产 API

实测反例：派工单要求"用生产 `save_*` 建字幕片段/评论/心理词/分类"，但项目里**没有这些写入 API**，
而同胞集成测试一律用既有夹具 `RepositoryRows.insert(<table>, **values)`
（`tests/integration/repositories/conftest.py`）→ 工人按约束做不了、按白名单查不到 → 停下索取，**白烧一轮 84k**。

正确措辞分两层：
- **被验证的写入路径**必须是生产仓储方法（这是卡的目的）；
- **种子行**用既有夹具（**点名文件+类+行号**），并写明「禁的是生产代码里直插 ORM 与手搓持久化 JSON，
  **不是**禁测试造种子」。

## 4. 根因通常在**卡面**，不在工人

`--cov` 目标漏掉某模块 ⇒ 该模块 0 覆盖也能"达标"，门槛形同虚设。
出卡/初审固定加一条核对：**本卡 `--cov` 目标 ⊇ 本卡写入的模块**
（卡08 就是这样把 313 行真 SQLite 仓储埋成了 0 覆盖，直到回查老账才发现）。

## 5. 回查老账的四把尺子（一次性，性价比极高）

1. 全量单次 `--cov=app` 对分层门槛；
2. **生产类名是否出现在 `tests/`**（`grep -rn "<ClassName>" tests/` 零命中 = 该类 0 覆盖）；
3. 该卡 `--cov` 目标清单 vs 该卡写入的模块；
4. 测试是否真走 SQLite（`grep -c MagicMock/Fake` vs 真连接）。
