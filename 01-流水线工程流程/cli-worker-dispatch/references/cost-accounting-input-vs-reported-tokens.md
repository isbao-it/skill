# 成本口径：工人自报的 `tokens used` 不是成本，`input` 才是（2026-09-19 实测校准）

配套 `scripts/codex_quota_audit.py`（读 `~/.codex/sessions/**/rollout-*.jsonl`，按会话汇总）。

## 一、症状：汇报出来的成本低了一个数量级

每轮 `codex exec` 收尾都会打印 `tokens used <N>`，看起来就是这一场的花费 —— **不是**。
实测同一场（卡12 R08）：工人自报 **324,964**，审计出的 **input 10,976,490**（89 轮）→ **差了 34 倍**。
拿前者做成本台账，会得出"一轮才几十万"的错误结论，进而错误分配额度。

## 二、审计脚本怎么跑

```bash
.venv/Scripts/python.exe -B \
  ~/.hermes/skills/cli-worker-dispatch/scripts/codex_quota_audit.py
```

输出（本机 2026-09-19 实测样本）：

```
会话数 130（含 token 统计 121）  轮数合计 2,898
input 285,999,500  cached 267,030,784  output 2,792,423
input : output = 102 : 1   ← 远大于 1 = 额度烧在上下文重放，不是产出
缓存命中 93%（前缀缓存只打折，不免费）
时间                模型            input        out     轮   每轮重放
2026-09-19T03:12   gpt-5.6-sol   10,976,490   44,922   89    124k   ← 卡12 R08
2026-09-18T10:35   gpt-5.6-sol    5,646,303   54,102   42    137k   ← 卡12 R01
```

读法：**「每轮重放」列 117k–150k** —— 这就是"一卡一会话、每轮重放整段历史"的代价；
所以省额度 = **压轮数 + 压每轮上下文**，两件都要做（薄卡、紧派题、只读白名单、少回读日志）。

## 三、汇报纪律（写给未来的自己）

- **成本一律用 input 口径**（审计脚本的数字）；`tokens used` 只能当"这一场跑了多少轮"的粗略信号。
- 报成本时**同时写口径**（例：`卡12 R08 ≈ 1,097 万 input（89 轮）`），否则跨会话对比会得出相反结论。
- 单卡预算参考量级：出卡/执行一场 **数百万 input**；一张大卡全链路可达 **千万级**。
  一旦发现某轮 input 异常高，先看**轮数**（轮数×每轮重放），别去猜"是不是写代码太慢"。
- 缓存命中率高不等于便宜：缓存只**打折**重放，不免费 —— 压轮数的收益是线性的。
