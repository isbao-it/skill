# 「写后报错」缺陷：只有动态复现能抓到，修法是先读后写（2026-09-19 卡12 实测）

## 1. 缺陷类别：被拒绝的请求照样产生副作用

实例（卡12，FastAPI 接口层）：

```
app/application/api.py::decide_proposal
  1) 先调 self._session_service().decide_proposal(...)   ← 这里改库
  2) 再校验 result.proposal.script_id != script_id → raise DomainError("not_found")
```

表现：路径 `script_id` 与提案实际归属不一致时，**HTTP 返回 404，但库里已经改了**
（实测：提案 → `ACCEPTED`、剧本版本 1→2、`proposal_decisions` 0→1）。

**这类缺陷静态评审极易放过**：代码读起来"有归属校验、会返回 not_found"，只是**顺序反了**；
只断言状态码的短用例也照样通过（404 断言成立）。属于"正确性 bug + 数据损坏风险"，必须抓到。

## 2. 检测手段：派工单强制「只复现，不改实现」的动态脚本

对任何**可疑的顺序/副作用**问题，派工单里写死这一条要求（本次由它一举抓到缺陷）：

> 写**独立只读脚本** `project/outputs/待审核/<卡>/R0x/details/repro_<name>.py`：
> **真 SQLite + 生产仓储/服务/门面**，构造边界/不一致输入，输出**结构化 JSON**，必须包含：
> `http_status`、`error_code`、以及每个受影响对象的 `<obj>_before` / `<obj>_after`、相关表行数 before/after。
> **不得**把该缺陷写成失败用例塞进 `tests/`（保持套件全绿）；**不得**修 `app/**`；原始输出落 `details/repro_<name>.log`。

要点：证据形态必须是**状态前后对比**，不是一句"返回 404"——否则看不出副作用。

## 3. 修法：先读后写（不是加重补偿，也不许改下层）

- 在**调用会写库的服务之前**，用**既有读能力**做前置校验；不通过就抛错，**写库之前**返回。
  例：`if proposal_id not in {p.id for p in self._session_service().list_proposals(script_id, owner)}: raise DomainError("not_found")`
- **不要**为了省事去改 `app/services/**`、`app/repositories/**` 或新增端口（那是越界扩范围）；
  优先在适配层用已有读接口组合出前置检查。
- 修完**必须原样复跑**同一份复现脚本，在 `details/` 留下 **"修复后"** 输出（期望：错误码不变 + **0 变化**）。

## 4. 回归测试的硬性双断言

只断言状态码 = 放水。必须同时断言：

1. **对外表现**：HTTP 状态 + 错误码（如 `404 not_found`）；
2. **副作用为 0**：目标对象状态未变（仍 `PENDING`）、版本/计数不变、审计/决策行增 0。

## 5. 同类排查（点名要求，不只修可见那一处）

派工单里加一句：「凡"**先调用写服务、再校验路径/归属/版本**"的路由，逐条过一遍，
同类缺陷一并报告与修复」——只修被复现的那一处不算完成。

## 6. 一句话记法

> **凡是在写操作之后才做前置校验的实现，都是缺陷候选**：动态复现证明它，先读后写修掉它，
> 用"状态 + 零副作用"双断言锁住它。
