# 产出被覆盖 / 整单空跑：两个实测案例（2026-09-17）

配套 `SKILL.md` §三（先看磁盘再决定重跑）与 §六（常见坑），以及
`references/worker-interruption-and-recovery.md` §5（从会话日志反解）。

---

## 1. `-o` 与产出文件同路径 → 正文被答复摘要覆盖

**根因**：`codex exec -o <文件>` 的语义是「最终答复落盘」。若 `<文件>` 恰好是派题里**让工人产出的那个文件**，
Codex 退出时会用自己的收尾摘要**覆盖**工人写好的正文。

**症状（一眼可判）**：文件存在，但**行数远小于工人自报**。
实测：工人自报 299 行裁决正文 → 磁盘上只有 34 行，内容是一段带 `tokens used` 的汇报摘要。

**处置**：
1. `wc -l` + 读前几行，确认拿到的是摘要而非正文（别急着以为工人在吹牛）；
2. 从会话日志反解取回正文：找 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` 中
   `payload.item.type == "FileChange"` 的记录，取 `changes[<path>].content` —— 一次成功、零额度；
3. 恢复后核行数/字符数；有 JSON 交付物则跑项目校验器再确认一次。

**预防（写进派工单模板）**：`-o` 只指向 `<同名>_日志.md` / `<卡号>_运行日志.md` 这类**独立日志名**，
绝不与任何产出文件同名。

## 2. `claude -p` 整单空跑的判读（会话日志在别处）

会话日志：`~/.claude/projects/<cwd 编码>/*.jsonl`。
目录名 = 工作目录把盘符冒号与路径分隔符都换成 `-`：
`C:\work\dev\projects\<proj>` → `C--work-dev-projects-<proj>`。

**判读三件套**：
- **运行中 stdout 0 字节属正常**：`claude -p` 到进程结束才 flush，别误判卡死、别急着 kill；
- **进程已退出 + 日志 0 字节 + 目标文件未改 = 空跑**：该次派工无效，直接按「新会话」重派，不要继续等；
- 打开该会话 jsonl：若只有 `last-prompt` / `ai-title` 条目、**没有任何 assistant 轮次或工具调用**，
  即为空跑的事后确证（是"确实没干活"，不是"干了但没回报"）。

**预防**：与 codex 通用 —— 一任务一会话 + 显式模型 + 独立日志路径（见 §1）；
换工人前先用最小探针确认通道（见 `references/worker-interruption-and-recovery.md` §1），
别把"通道空跑"误当成"任务太难"。

## 3. 顺带一条验收纪律：自报数据既可能虚高，也可能**过期偏低**

同一快照下，工人自报 `repositories/scoring.py` 覆盖率 47%（因其末次补强后未再测量，属于旧读数），
Hermes 独立重测为 95%。所以「不自报绿就信」要双向执行：**绿要重测，红也要重测**，
唯一可信的是自己在同快照上跑出来的数。
