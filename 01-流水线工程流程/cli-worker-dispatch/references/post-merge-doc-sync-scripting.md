# 合入后文档同步：先学真实行格式，再让每个目标独立落盘（2026-09-18 卡10 实测）

配套（不替代）：`references/initial-review-gates-and-scripted-doc-edits.md` 第二节（`re.M` 与命中数断言）、
`references/post-merge-archive-integrity.md`（归档与待审核区清理）。

「合入后同步」= 改卡面 `status`、改模块文档状态行与实现要点、改模块 README 表格行、改进度快照行与提交链 ——
这一步几乎每张卡都做一次，脚本写错一次就白烧半个回合。

## 一、真因常常是**格式假设错**，不是正则写法错

卡10 的同步脚本报 `AssertionError: 0`，改的是 `docs/modules/10_review.md` 的**状态行**。
脚本按普通行写 `(?m)^- 状态：.*$` / `^状态：.*$`，而该文件里真实形态是**引用块**：

```
> 状态：架构/任务卡已定义，尚未据本模块执行实现与测试。依据：架构 §9.3、§9.7、§9.8.6、§9.8.13 及卡10裁决。
```

同类「看不出来」的形态差异（都实测过）：

| 目标 | 容易假设 | 实际 |
|---|---|---|
| 模块文档状态行 | `状态：…` / `- 状态：…` | `> 状态：…`（引用块） |
| 模块 README 表格行 | `\| 10 \| … \| 待拆 \|` | 单元格里有 `✅ 已实现并合入（<hash>）` 之类变体，需**整行替换**而不是局部 |
| 双卡状态 | `- 状态：待执行` | YAML frontmatter `status:` 单独一行 |

**对策（成本≈0）**：写脚本前先打印目标文件头几行，看清真实形状再动手：

```bash
.venv/Scripts/python.exe -c "import pathlib;print(chr(10).join(pathlib.Path('docs/modules/NN_xxx.md').read_text(encoding='utf-8').splitlines()[:10]))"
```

锚点仍按上一份参考的规矩：**最短稳定子串 + `re.M` + `re.subn` 断命中数**。

## 二、一个目标一段代码，各自打印 `ok`；别写成一条长链

一条长链里第一个 `assert` 炸掉，**后面所有目标会静默不执行**。
卡10 实测：模块文档状态行与实现要点**已改成功**，README 表格行与双卡 `status` **一个字没动**，
但脚本已在第一条断言处退出 —— 若此时直接向用户报「同步完成」就是误报。

```python
targets = {
    "模块文档状态行": ...,
    "模块文档实现要点": ...,
    "README 表格行": ...,
    "任务卡 status": ...,
    "测试卡 status": ...,
}
for name in targets:          # ★ 逐目标独立，失败只影响自己
    try:
        ...re.subn(...); assert n == 1, name...
        print("ok", name)
    except AssertionError:
        print("miss", name)
```

## 三、中断后先核「哪些已落盘」，再决定重跑

不要假设「什么都没发生」。先看实际改动面：

```bash
git status --short && git diff --stat
```

重跑脚本要**幂等**：已改过的目标不会再命中，断言会红 —— 此时应把「已是目标态」判为通过
（例：状态行已是 `已实现并合入` 就跳过），否则会在「修好了一个、撞红了另一个」之间来回。

**判据**：脚本输出里每个目标各有一行 `ok`；提交前 `git diff --stat` 的文件集合与预期清单逐项一致，
且快照行/提交链/覆盖率数字与本次实际验收值一致（不写未验证的数字）。
