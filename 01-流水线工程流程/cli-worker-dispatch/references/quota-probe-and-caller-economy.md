# 额度探活、并行派工与「调用方也要省钱」

来源：2026-09-17 一天内的实测（出卡烧 82,395 token 零产出、用户明确纠正调用方成本、用户要求并行跑两张卡、验收门槛改为按需手测）。

## 一、派大活之前先探活（1–2k token）

**教训**：额度只剩一点时直接派大活 → 烧掉几万 token 后撞限、**一个文件都没写**。本机实测：出卡任务 `CARD_EXIT=1`、`You've hit your usage limit … try again at 10:32 PM`、烧 **82,395 token**、产出目录为空。

**做法**：把探活与正式任务用 `&&` 串在**同一条后台命令**里 —— 探活不过就不会启动正式任务，也不必人工盯着：

```bash
cd <项目根> && mkdir -p project/outputs/<NN> \
  && codex exec -m <模型> --skip-git-repo-check -C "<项目根>" "只回复两个字：正常" > outputs/探活.log 2>&1 \
  && codex exec -m <模型> -c model_reasoning_effort="high" -c sandbox_mode="workspace-write" \
       -c approval_policy="never" -C "<项目根>" --skip-git-repo-check \
       -o "<产出>_日志.md" "$(< 提示词文件)" > "<产出>运行.log" 2>&1; \
  echo "EXIT=$?" >> "<产出>运行.log"
```

探活成功时可看到 `PROBE_OK` 之类的回显（放在 `&&` 链里先 echo 一句，日志里一眼能确认）。

## 二、并行派工：可以，但要带闸

- 用户可能明确要求「开个并行跑 X」；本机实测两个 `codex exec` 并行**都正常跑完**（各自 exit 0）
- 先诚实提示：同一账号并行会**争订阅额度**，一个撞限可能把另一个一起带走
- 两侧都要有熔断：任一报用量上限即停；撞限的那条**降级串行重排**（排在另一个之后），**不重派、不烧第二轮**
- 别把并行当成"加速免费"：真正省时间的做法是让两条线各自都能独立收敛（出卡线 + 执行线），而不是让两条重活抢同一份额度

## 三、调用方自己的 token 也是用户的钱（用户原话：「你做的话烧的是我的钱」）

额度紧张时，**不能只省工人的额度**。调用方（Hermes/主代理）自己也要省：

| 省法 | 具体做法 |
|---|---|
| 回读克制 | 日志只取**退出码 + 末尾摘要**，不 tail 大段（尤其别把 UTF-16 的 pip/命令日志整段读回）|
| 命令合并 | 一次调用把「退出码 + 范围 `git status --short` + ruff + 定向 + 覆盖率」合成一条 |
| 免重复复跑 | 工作区没变就不重跑全量；合入前后不再各跑一遍 |
| 不返工装饰件 | 一处措辞瑕疵、行尾粘连、0 字节日志 → 攒着一起处理或直接放过，**不为它单派一轮工** |
| 报告简短 | 表格化、少贴长文；结论先行 |

## 四、验收门槛：自动测全绿即可合入（2026-09-17 用户改）

用户明确：「暂时没必要非要让我手测，以后遇到自动测试不了的再让我手测」。

- **合入门槛**：定向通过 + 覆盖率达标 + 全量回归 + Ruff + `summary.json` 校验器判据 **0 ERROR 0 WARN** + 证据文件存在性 + 范围/零迁移核对 —— 全绿即可合入
- **只在这些地方请用户上手**（请示时必须写明「为什么自动测覆盖不到」）：UI 交互/视觉效果、真实模型或真实联网、Compose 端到端、首次下载/安装类一次性动作
- **仍然保留**：合入代码前要用户一句话批准（🟢/短指令）—— 这是「什么进主干」的开关，与手测是两件事
- 收益：少掉每卡一轮"等用户手测"，本项目 9 张待做卡合计省 2–4 个工作日
