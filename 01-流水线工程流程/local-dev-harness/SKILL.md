# 本地开发栈启动与 IDE 集成（后端 + 前端）

适用于「把本地开发的多个服务（FastAPI/uvicorn + Vite、或同类前后端）起起来、让用户能点开页面看效果」这类工作。
用户是初学者：他要的是**能自己一键起、看得到日志、点得开页面**，而不是你替他起一次。

## 何时用

- 用户说「帮我把前后端跑起来」「在 VSCode 里打开后端和前端」「刷新看效果」
- 需要交付一个可交互的本地环境（UI 手测、联调、验收演示）
- 服务起不来/端口占用/前端请求 403，需要定位
- 要换/接入真实 LLM Provider（改 `.env` 里的密钥、base_url、模型名），或排查「配都配了却调用一直失败」

## 一、先探后起（不要凭记忆写命令）

1. **从仓库读真实命令**：`pyproject.toml` / `package.json` 的 scripts / `AGENTS.md` / README / CI 配置。
   不要套用通用记忆（端口、模块名、包管理器都可能不同）。
2. **确认解释器与运行时**：项目 venv 解释器（如 `.venv/Scripts/python.exe`）要**实际存在**，`node -v` / `npm -v` 要真查到版本。
3. **确认端口空闲**：起之前查监听；已占用先问清是别人的进程还是自己的残留（只按 PID 点杀，禁按名字批量杀）。
4. **确认本地配置到位**：`.env` 等本地文件存在且含开发所需开关（例如关掉 HTTPS-only Cookie）。
   密钥只放**被 gitignore 的本地文件**；仓库内的示例文件只写注释、不写值。

## 二、交给用户一键起（VSCode 集成，用户偏好）

本用户明确要「在 VSCode 里面打开后端和前端」→ 交付 **`.vscode/` 三件套**，而不是让他背命令：

- `.vscode/tasks.json`：每个服务一条 `type: shell` 任务（`isBackground: true` + 带 `endsPattern` 的 problemMatcher），
  再加一条 **compound 任务**（`dependsOn: [...]`）作为「一键起全部」；另配「跑测试」「覆盖率」任务。
- `.vscode/launch.json`：后端 `debugpy`（`module: uvicorn`）+ 前端浏览器调试（Chrome/Edge，url 指 dev server）。
- `.vscode/settings.json`：`python.defaultInterpreterPath` 指项目 venv、开启 pytest、`files.exclude` 隐藏缓存目录。

可直接照抄改的模板：`templates/vscode-harness.jsonc`。

交付时用**用户的操作路径**说一遍：`Ctrl+Shift+P → Tasks: Run Task → 「启动全部」`，然后打开哪个 URL。

## 三、服务生命周期纪律（踩过的坑）

- **不要把长驻服务放在自己的前台调用里**：前台调用有超时上限，超时会连带杀掉整棵进程树（把服务、甚至你
  正在跑的工人一起带走）。需要自己起一遍做验证时，用**托管的背景进程**（`background=true` + 完成通知）
  或立即返回式启动。
- **验证完要按 PID 关掉自己起的服务**，否则端口被占，用户随后用任务起会失败。
- **就绪判定用探针，不用 sleep 猜**：对后端打一次 HTTP（健康/文档端点），对前端确认端口在监听，
  再回读日志尾部确认无异常。
- 服务起不来时**如实报告原始报错**（缺模块、缺 .env 键、端口冲突），不要反复重启掩盖问题。

## 四、npm / Windows 常见坑

- **npm 参数透传**：`npm run <script> <flag>` 会被 npm 自己解析，未知参数直接报 `EUNKNOWNCONFIG`
  （实测 npm 12 下 `npm run test -- --run <file>`、`--reporter` 都中招）。
  正确写法是 **`npm run <script> -- -- <flags>`**，或直接调底层 CLI（如 `node node_modules/vitest/vitest.mjs run <file>`）。
  **写进任务/卡面/文档前先真跑一遍**，否则用户照抄必失败。
- **任务里的路径**：Windows 下 JSON 里的反斜杠要转义；用正斜杠（`${workspaceFolder}/.venv/Scripts/python.exe`）更稳。
- 前端 dev server 只监听 localhost/IPv6 时用 `http://localhost:<port>` 访问最省事；换 IP 或远程访问会被
  dev server 的 host 白名单挡掉。
- shell 是 git-bash 而任务是 PowerShell/CMD 时，同一句命令语法可能不通——脚本类命令优先写进 `.sh`/`.ps1` 文件再调。

## 五、本地可交互所需的「开发桩」

当一个功能依赖外部服务（真实模型、第三方 API、联网、付费额度）而本地起不来时，**不要用假数据糊过去，
也不要让用户干等**：要求/派生一张「开发桩」小卡，在本地打通链路 —— 桩必须**显式开关（默认关闭）**、
**不联网**、**不读密钥**、**确定性**、**启动有告警**，保证生产绝不可能误开。
桩就绪后再请用户做人工手测；在此之前相关人工项**如实登记为未验证**。

## 六、接入或切换真实 LLM Provider（先探后改，能纯配置就别动代码）

适配器已做成「换厂商只改配置」时，**只改 `.env`，不要动代码**——改代码要走卡。
完整清单、厂商差异与判读阈值见 `references/llm-provider-switch.md`。

1. **先只列键名，不打印值**：`python scripts/probe_openai_compatible.py --env-file .env --list`。
   用户说「我在 .env 里加了个新密钥」时，很可能是把值贴进了已有变量名（或新增了同名行）。
   载荷取**最后一次出现**，于是旧厂商的密钥被顶掉、base_url 还指向旧厂商 → 每次都 401。
   修法是把值搬到中性槽位（`LLM_API_KEY` + `source=generic`），不要覆盖厂商专有变量，也不要删旧值。
2. **先验密钥与地域配对**：对候选地域各打一次 `GET <base>/models`（200 = 配对，401 = 密钥不属于该地域），
   并从模型清单里**逐字**取模型 id（`qwen3.7-flash`，不是 `Qwen3.7-Flash`）。
3. **按清单切换**：base_url / 密钥来源(+密钥) / 每个模型槽位 / 结构化输出档 / 费率与费率来源 / 超时。
   旧厂商的那几行以注释形式留在同一处，并在文件头写清切换步骤，否则下次切不回去。
4. **费率写清口径**：字段常是无货币浮点，把**币种 + 档位**写进费率来源字符串；
   按输入长度整单重算的计价（如 32K / 256K 两档）要在注释里写明阈值与后果。
5. **验证走项目自己的适配器，不要用 curl 交差**：复用适配器自己的请求体构造函数拼出与生产一致的请求，
   批处理链路 + 创意链路各跑一条真实调用，断言结构化输出与 usage 都被解析；再跑定向测试确认无回归。
6. 改前备份成 `.env.bak-<原因>` 并确认被 gitignore 覆盖；**改完必须重启后端**（见下一节）。

### 思维链默认开启 × 严格 JSON 契约（最容易漏的兼容性坑）

新一代模型（如 qwen3.5/3.6/3.7 系列）默认开启思考模式：`prompt_json` 档下实测 10 次里 5 次把 JSON
包进 ``` 围栏，而严格 `json.loads` 的适配器不剥围栏 → 稳定报「响应结构非法」；思考 token 还会让单次输出
涨约 10 倍、延迟到 12~27 秒。

- **纯配置的修法**：结构化输出档切 `json_schema`（端点侧约束输出），围栏归零。
- **更彻底的修法**：请求带 `enable_thinking=false`（延迟 ~2.4s、输出 176 vs 1738 token）；
  适配器没有传额外参数的位置时这属于**代码改动，要开卡**，不要顺手改冻结区的常量或签名。
- **一律用抽样实测下结论**：同一请求连发 10 次，统计「干净 JSON / 围栏 / 其他失败」+ 中位耗时 +
  中位输出 tokens，用数字回答「这个模型能不能用」，不要凭感觉。

## 七、交付前：**自己先走一遍真实链路**（不把坑留给用户）

自动测试全绿 ≠ 用户点得动：测试跑在夹具里（mock 传输、临时库、pytest tmp），用户点的是真实进程
（真 `.env`、真数据目录、真浏览器、真 Origin/CSRF）。**在请用户手测之前，调用方先自己把环境搭好并走完整条链路**，
步骤、探活脚本写法与隔离核对清单见 `references/pre-handoff-runtime-smoke.md`。四条铁律：

- **改了 `.env` 必须重启后端**：`--reload` 只盯 `.py`，不会重读 `.env`；否则服务仍是旧配置，报错与你的配置对不上。
  停旧进程只按 PID 点杀；若那个进程是用户用 VSCode 任务起的，**明确告知**（他的终端会显示进程已停止）。
- **多闸门配置先读源码字段名与字面值**，再写 `.env`：按文档/裁决里的示例猜键名会得到稳定错误码（如 `invalid_config_value`），
  看着像配置错，实则闸门条件或取值字面值不符。
- **初始化/种子 CLI 报稳定错误码时，先读源码定位守卫条件**（`grep -n "<错误码>" -B12 <file>`）再改命令：
  典型是 `--reset` 走 fail-closed —— 拒绝没有标记文件的目录（防误删正式库），**首次建库必须不带 `--reset`**。
- **交付清单只说用户要做的**：能点的 URL、点哪些按钮、哪些前缀是刻意的假数据标记、
  以及**自动测试覆盖不到、只能他手测**的那几项；其余（起服务、初始化、配置）都由你做完。

## 八、报告口径

- 先给**能点的 URL** + 服务各自监听在哪，再给命令。
- 明确说清哪些**验证过**（探针返回、端口监听、日志尾部），哪些**没验证**。
- 用户改代码后提醒一句「热更新会自动生效，刷新即可」。
- 用户问「A 换 B 怎么样」时给**表格**：两边的配置费率、实测耗时/token 数、能力差异（多模态、上下文），
  并明确写清**没验证的部分**（你查不到的模型质量分数就直说查不到，建议用项目自己的用例跑一次 A/B）。
  你自己可能就跑在被比较的模型上，如实说明这点，别装作中立第三方。
