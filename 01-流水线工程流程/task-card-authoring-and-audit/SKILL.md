# 任务卡/测试卡的出卡、修订与终审前审查

适用于「架构师或工人产出任务卡+测试卡 → 我审查 → 用户终审 → 派工 → 验收」这类流程的**卡面侧**
（工人侧/验收侧的派工方法论另见 `cli-worker-dispatch`）。

## 一、卡的生命周期：谁写、写到哪一轮

典型链条（每轮只重写局部，所以缺陷多为「改了一节没回头改依赖它的节」）：

1. **出卡前取证**：见 §五。禁把"我以为的形状/现状"写进派题。
2. **架构师/出卡轮**：产出「裁决 + 任务卡 + 测试卡」。要求：事实基线、方案对比、行为组、真实形状表、
   真跑验收口径、不做清单、待用户拍板决策表。
   - **派题给「契约型交付」时（固定章节表 / 模块文档模板 / 卡面必需字段）写死两条**：
     ① **不适用的小节保留标题 + 一行理由，禁编造、禁为凑章节虚构设计**——不写这条，工人会为了让它「有用」而发明内容，
     那是幻觉的直接来源（零构建小项目实测固定章节表里近半属于此类）；
     ② **发现上游权威文档内部矛盾时停下报告**：把矛盾、算术推导与两条候选修法写进文末「待拍板」，
     **禁自行改上游文档、禁默默按一种读法实现**——这是把矛盾变成可裁决资产、而不是缺陷的关键一步。
3. **压回轮**：只压字数、不改要求；压完全套核对（§四）。
4. **修订轮**：把用户拍板折进卡面（端口签名/配额/开关/错误码）。
5. **微修轮**：修内部矛盾（§四第 4 条）。
6. **终审包**：把「最终卡面 + 验收 GWT + 禁止行为」三块端给用户 🟢。卡未终审不派工。

**串行纪律**：第 3/4/5 轮**不许并发**——同一对卡面文件两个写手会互相覆盖。每轮独立复验通过后才进下一轮。
派每一轮都把「权威依据文件 + 当前字符数 + 上限 + 禁改文件」写进派工单。
**档位（模型 + effort）也写进派工单**：判断类（出卡 / 架构 / 裁决）才用 sol，提取与逐字替换类
（模块文档、错误码表、文案同步、按行号微修）一律 luna —— 判据、实测额度数据与度量脚本见 `dev-pipeline-governance` §3。

**拒绝轮（`<卡号>b`）的纪律**：卡被验收驳回时**不要重出整卡，也不要推翻已通过的部分**——先判「未过的硬指标有哪几条」，
卡面只写这几条，并把**已通过的部分点名「必须保留」**（实测：布局卡只挂「加满数据后整页仍滚动」一条；不点名保留，重做时会顺手把已压缩好的顶部区改回原样，白验一遍）。
另一半是：**给验证过的配方，而不是目标描述**。凡是工人没有真跑环境的那类口径（浏览器布局/视觉/真机），
调用方先把修法在真环境里实测验证（如页面内注入候选 CSS → 复量 → 移除探针复量，三步才能定因果），
再把**验证过的具体做法精确到属性/参数**写进卡面；只给目标描述等于让工人猜，必然再错一轮。
布局类口径的量测与退回卡三件套见 `delegated-output-verification` 的 `references/ui-viewport-layout-acceptance.md`。

**切片表（卡片要并发执行时）必须回答两个可判定问题**：
- 每片写清「**本片验收命令**」+「**依赖的片**」。判定句：*这片在**自己的 worktree 里**能跑完它自己的验收命令吗？*
  不能 → 不能并发（**接口冻结 ≠ 实现就绪**）。**编排/装配类片天然是最后一片**，它与实现片并发只会在 worktree 里连环受阻。
- **并发片开工前，调用方先把「共同基线」落盘并 commit**：依赖清单与锁文件（`package.json` + 锁）、测试运行器与覆盖率插件的安装、
  vendored 第三方库、探针夹具、冻结文档与模板的**仓库内副本**。让每片的 worktree 从**同一个 SHA** 长出。
  漏这一步的后果不是报错，而是**每片各自引入依赖 / 各自定夹具形状**，合并时全在接缝上爆；
  且卡面里的验收命令（`npx --no-install vitest run tests/x.test.js`）在工人沙箱里根本没有可跑的二进制。
  判定句：*这条验收命令，在刚拉起的干净 worktree 里能直接跑吗？*不能 → 基线未就绪，先落基线再派工。
- **装配/收口片的验收口径必须自带「离线 harness」**：这类片自己跑不起来（它调用的实现属别人），若卡面只写「人工核对一下」
  或「mount 一次看有没有报错」，它的片级自验就退化成静态核对，接缝缺陷只能留到包末甚至用户手里。卡面写死：
  交付一个**离线可跑**的 harness（隔离 document + 记录型端口 + 可控 promise 注入**真实装配入口**），
  分别断言端口调用参数与只读性、时序竞态、负向路径。配方见 `delegated-output-verification` 的
  `references/offline-spa-browser-acceptance.md`。
- **止损判据**：同一片连续 **2** 轮无实质产出（只交草稿 / 只交阻塞报告 / 只交配置项声明）→ 立刻换策略，
  **禁第 3 次原样重派**：① 再切一片更小的（只含一个可独立真跑的目标）；② 并回主工作区、升一档一轮收口。
  实测某片连 6 轮未闭环、合并后一轮即成——「升档一轮」比「重派三轮」便宜。

## 二、卡面预算（超出即退回重压，不商议）

- 执行卡 ≤**8000** 字符、测试卡 ≤**6000**、两者合计 ≤**14000**；**行为组 ≤8**（参数化样本不设限），
  超出即拆卡。
- **一律用字符口径，且只有一种算法**：`len(open(p, encoding='utf-8').read())`。
  **`wc -c` / `ls -l` 是字节数，不是字符数** —— 中文 markdown 实测虚高约 1.4~1.5 倍（同一份卡：7998 字符 = 11299 字节）。
  拿字节数当字符数会把**合规卡误判成超限**，白派一轮压回轮、把卡面内容压掉一层（实测发生过：原稿本就在 8000 字符内）。
- 加内容必然顶到上限：派修订/微修轮时明确写「**改完自己报实测字符数**」，不要自己估。
- **禁成段复制**架构/模块文档章节与整表；但**枚举值 / 字段名 / 错误码 / 表物理名 / 阈值必须钉进卡**。
- **撞上限时改「分发方式」，不是压内容**：大段冻结物（用户可见文案表 / 签名表 / 枚举表）逐字抄进卡面**必然**顶破
  8000/6000/14000 —— 压回轮只能把内容压掉一层（实测两轮出卡的唯一退回原因就是这个）。
  正解是把它降为**引用**：架构里那一节是**唯一权威**，用 `tools/frozen_check.py extract` 生成机器可读的
  `project/frozen.lock.json`（文案 / 枚举 / 函数 / 标准值 + 该节 sha256），卡面只写「**本卡用到的键名清单** +
  指向 lock 的路径」，lock 进「输入文件（读取白名单）」。这样「卡面自足」与「≤8000 字符」不再打架，一致性由工具保证。

## 三、卡面必须是**可判定**的

- 每组 Given/When/Then 要能被一条用例判真伪；禁「完整实现 X」「保持高质量」这类空话。
- 硬边界逐条写：只改白名单文件、**禁顺手改文档**、不新增依赖、禁 git 操作、不放宽/删除既有断言。
- **卡面自足（引用必须可达）**：凡写「按 X 文档 §Y 实现」，X 必须出现在「输入文件（读取白名单）」里；
  不在就把**那一节的冻结物以 lock 形式发到卡面**（`frozen_check.py extract` 生成 `project/frozen.lock.json`，
  进读取白名单 + 卡面点名本卡用到的键名）；只有在该节很短且无处可引时才逐字内联（常量/枚举/签名）。
  校验动作：终审与每次验收前跑 `python tools/frozen_check.py check <lock> <卡面> <模块文档…>`（流水线 `tools/`），
  退出码非 0 = 契约漂移，**不得进验收**。悬空引用 + 白名单不含它 = 工人只能凭猜测写接口，
  或越界去读白名单外文件——两条都是红线。反过来说：卡面已被内联到自足时，就**不要把架构大文档放进白名单**（省上下文）。
- **凡「可复制 / 可导出 / 可打印」的产出，卡面必须给一条「定例」**：给定输入 → **期望的完整输出字符串**
  （含表头行、分隔行、空值写什么字），而不是「生成 Markdown 表格」这种描述。同类：空值在数据层与展示层各写死一种
  表示（如矩阵空位唯一 `null`、展示为「空」字），禁 `''` / `undefined` / 同名字符串混用——混用会在「名字真的叫空」时炸。
  判据句：*这条输出能不能一眼比对？给定输入是否只有一个正确字符串？*
- 开关型功能（默认关闭的 ASR / 真实 LLM / 外部推送）必须在卡内安排**一次真跑验收**（开关开 + 真实样本
  + 真库行级核对），否则等于未验。
- **真跑验收要写「四条真实」**：真入口（从用户会执行的 CLI / 装配入口进，不能只测内部函数）、真形状（夹具复刻真实
  返回值的**结构与条数**）、真状态（租约 / 中断 / 配额用真实库造，禁 mock 字段）、真注入（配置以环境变量字符串
  形态验证，默认值 / 原生类型直传会掩盖解析缺失）。缺哪条，哪条路径的缺陷就留到上线才炸。
- **每条被声明支持的路径各要一次真跑**：卡面写“支持 A/B/C 三种来源”就要求三条各跑一次并各自留库内证据；
  “跑通一条”不代表其余（实测：B 路径真跑全失败，而 A 路径与单测全绿）。
- **有持久化的模块，卡面必须指定「状态由谁负责重建」**：若业务层冻结接口里**没有恢复入口**，
  界面层只能自己重算业务周期与累计计数（必然违反分层铁律），而算错只在真刷新时暴露。
  卡面要么给业务层一对 `snapshot()` / `restore(snapshot, nowMs)`（并同步冻结计数与全部调用方），
  要么把重建算法与**断言**（「恢复后累计计数必须等于存储值」）逐字钉进卡面 ——
  禁只写「刷新后状态恢复」这种不可判定的措辞。
- **中断/续跑类行为必须有「真中断」验收**：卡面写明用真实库造出「任务处于执行态 + 租约已过期 + 进度非空」
  再重入，断言不重复取数、计数不重复计、能推进到终态。
- 错误码要诚实归因：兜底不得把「任何非领域异常」收敛成某个业务码（会把排查引向错误方向）。
- **用户可见文案要作为冻结值逐条钉死**（凡卡面要求逐字实现的提示语）：每条一行给「错误码 / 文案（逐字，≤30 字）/ 展示位（DOM 区域）/ 触发条件」。
  ① **逐字复用需求文档里已有的文案**（如「未读取到学生名单」「有 N 人未分配」、空位显示「空」），禁改写；
  ② 占位符写成**可复制**的形态（`有 ${N} 人未分配`），禁「N 人未分配」这种读法不唯一的写法；
  ③ **不同错误码不得共用同一文案**；确需共用（两个内部码对用户是同一件事）必须显式写「与 X 共用」并说明理由
  ——不写，三片会各写一套，真跑时同一现象出两种提示；
  ④ 兜底文案禁回显底层异常原文与名单内容。**文案不冻结 = 把一致性交给每个片各自发明。**
  范本：`有 ${N} 人未分配`（N=未分配计数）/ `未读取到学生名单`（空表与零列共用，显式标注）——同一份表里既给文案又给共用关系与展示位。
- **验收判据必须是「时间稳定」的**：数据来自平台列表/分页/搜索时（顺序与候选集合会随时间轮换，
  实测同一查询相邻两次候选 **0/20 重叠**），**禁**把「再跑一次必然全是重复 / 顺序不变」写进判据——
  它会在真实运行里假红，然后被误判成产品缺陷，白搭一轮。只许写两类判据：**不变量**（唯一键无重复、
  库内行数守恒、账户余额平衡）与**同一次运行内立即复跑**能观察到的行为；只能跨时间成立的现象要求记 INFO、不判 FAIL。
  卡面要同时写明「该现象允许波动」，否则验收时会把它当失败。
  （同类脚本侧规则：手测脚本的判定段只写不变量，见 `windows-hermes` 手测脚本交付条目。）
- **假红的反面：循环推进型状态机必须有「跨多段跳变」用例，否则假绿**。凡被测对象是「推进到追上时间」的
  循环状态机（倒计时/限流窗口/重试退避/轮转周期），卡面必须要求一条用例让**单次推进跨越 >1 个完整段**
  （如传一个跳过 2~3 个番茄周期的 nowMs）。理由：把「每段用新的起点重算剩余时长」写成近似的实现，在
  「一次只跨一段」的用例里输出完全正确——只有多段跳变才会暴露计数少算与剩余时长偏移。
  卡面同时给一条**定例**（具体入参 → 具体期望值，含剩余毫秒与累计计数），让卡01 与后续装配卡复用同一组数，
  比写「状态转换正确」可判定得多。

## 四、终审前的固定核对（十四条，未过不端给用户）

1. **体量**（字符口径）+ **行为组数**。组数用
   `grep -o 'BG-0[0-9]' <卡> | sort -u` 数**唯一编号**——`grep -c 'BG-0'` 会把目录行/汇总行算进去，
   实测虚报（8 组被数成 9）。
2. **冻结计数双向核对**：卡面写 `67→68`、`50→51` 这类，**断言侧**与**对象侧**都要实测：
   ```bash
   grep -n "assert sum(" tests/unit/repositories/test_repository_contracts.py
   ./.venv/Scripts/python.exe -c "from app.domain.ports import CaseRepositoryPort as P; \
     print(len([m for m in dir(P) if not m.startswith('_')]))"
   ```
   - **规格里的「隐含计数」必须自己枚举实测，不许照抄**：外部文档把一组方法/枚举写成几段列表时**并没有给出数目**；
     逐个抄出来数一遍，再把「实数核对、非估算」写进冻结物。文档的叙述分组数与实际条目数常年不一致
     （实测：读起来像 10 个方法，逐条枚举后是 11 个）——照抄分组数，工人开工即对该计数断言全红。
   不一致 → **先修卡再终审**（工人开工就照错数字写联动断言 = 白烧一轮）。
   **改常量/上限/签名时，旧值会留一串「过期断言」在后面**：卡面只点名一处远远不够
   （实测卡面点了 `test_bilibili.py:535`，另有一条 GWT 用例仍断言旧上界「51 非法」→ 工人照卡做必然红）。
   定稿前跑 `grep -rn "<旧字面量/旧上界>" tests/`，把断言旧口径的**每个文件与用例名列进卡面**
   「需同步更新的断言」清单；漏一条，工人要么卡住、要么私自放宽断言（后者更贵）。
   - **扩展协议（新增端口/接口方法）的爆炸半径是另一套**，光点计数不够：受影响的是 ①协议的**全部实现者**——包括前卡标「禁改」的那个实现（卡面必须明写它本轮是同步更新还是保持不动；不写，工人只能越界或合法停摆）②**硬编码方法名集合**的用例（不只计数断言）。定稿前扫两类：`grep -rn "<新方法名>" app tests` 与 `grep -rn "<旧方法集字面量>" tests/`，把命中的每个文件与用例名列进卡面「需同步更新的断言」清单。
   **终审与每次验收前先跑冻结物一致性校验**：`python tools/frozen_check.py check project/frozen.lock.json <卡面> <模块文档…>`，
   退出码非 0 = 契约漂移不得进验收。它专抓三类**没有测试会红**的文档层错：漏冻结的文案（派生文档里还写着「原文待定 / 待确认」）、
   冻结计数漂移（架构冻结节与模块文档/卡面不一致）、残留占位词。改契约的唯一路径是
   **改冻结节 → 重新 extract → 全员按新 lock 对齐**（禁只改派生文档）。
   - **跨片/跨卡的「预期红」要写进卡面**：当某条既有断言的红是**批准扩展的必然后果**、而修它的实现属于别的片/别的卡时，卡面必须写明「该用例本轮必然红、由 X 片转绿、**禁**改它/禁 xfail/skip」。不写就会花掉一整轮：工人要么越界去实现别人的片，要么私自降门槛，要么诚实报 FAIL 而无人能判。
   - 同上：卡面把「实现属别的卡」的活写清楚时，要同时给出**该片无法独立验收**的说明（如“本片验收=编译/单元可过，端到端归后卡”），否则工人会拿一个它注定达不到的口径把自己判死。
3. **点名标识扫描**：用小批量关键串确认压缩/修订没把要命内容压掉——真实形状值、真跑验收口径、
   新增错误码名、冻结计数、不做清单。缺失即退回重压。
4. **内部矛盾扫描**（两类，按类找而不是通读）：
   - **同源数字型**：新引入的可配置量（"每日配额默认100、上限500"）与既有硬编码上限（"单个1..50"）**同源**，
     两处并存 → 无人知道谁生效。裁定模板：两闸**分别命名并写清谁截断谁**；常量改成语义单一的硬上限
     `..._CEILING`、旧名删除；**点名所有要同步的冻结用例文件及断言**。
   - **契约能力型**：某处刚把契约收窄到"不提供"，另一处新功能却要那份数据。实例：端口定为"只返已校验 ID"，
     同卡新 CLI 开关却要打印分布 → 工人只能越层或改端口（两条都是红线）。裁定模板：该能力落在
     **具体适配器/装配层的公开只读方法**上（沿用既有装配体例），卡面明写"端口不动、端口方法数不变"。
   - 通则：契约一旦写明"只返 X / 只读 / 不新增方法"，出卡时**逐个新功能追问「它需要的数据从哪来」**。
5. **卡面数字 vs 代码事实**：控件名/错误码/字段名/物理表名落卡前 grep 一次确认拼写与存在性；
   API 载荷契约若早已定义（schema 里已有 `mode` 之类字面量），直接引用它而非重新发明。
   **GWT 里点名的每个「可观察结果」同此办理**：统计项 / 阶段文本 / 样式类都要在冻结的元素表或字段表里找得到。
   实测卡面写过「任务总数统计相应减少」，而界面上**根本没有「任务总数」这一统计项**
   （只有完成番茄 / 专注分钟 / 完成任务）—— 观察点不存在，这条验收就无法判真伪，工人只能自己换一个地标来解释它。
   改写成真正存在的地标（如「该行消失 + 完成任务统计 -1」）。
6. **改写范围的爆炸半径 vs 白名单**：凡改动落在**共用 helper / 常量 / 签名**上，`grep -rn "<符号>(" app tests`
   列出**全部调用点**，逐个判定「在写白名单内」或「明确不受影响」，结论写进卡面。
   实测形态：一个 `validate_limit` 同时服务「评论条数（≤100）」与「批量条数（新上界）」两种量纲，
   而评论那条路径的**文件被卡面标成只读** → 工人正确实现后把评论上界一起松开，既过不了旧断言、又无权去修那个调用点，
   只能**合法停摆**（它会如实报「我开不了这个口子」，这一轮白烧）。
   裁定模板（同源数字型的孪生）：helper 加**显式 keyword 参数**（`ceiling=...`，默认值保持既有量纲）、
   **各调用路径各自传上界**；**禁**用一个新默认值顶掉旧默认值去悄悄影响另一条路径；
   被影响的调用点要么进白名单，要么在卡面写明「本轮不动它，故其断言保持」。
7. **配置项「减配」后的悬空断言**：用户拍板「少配置」（把时刻/词表/上限改成模块级常量）时，卡面必须同时给出
   三样：常量的**值**、**来源**（探针实测 / 架构条款）、**「改动需改代码」的代价说明**；并逐条处理原本依赖该配置项的断言
   （`grep -rn "<旧配置名>" app tests`）——删项而留断言 = 工人开工即红。自动路径走常量、手动路径仍走载荷，
   两条各留一条验收，否则删掉配置项会把那条路径的覆盖一并悄悄删掉。
8. **断言可观测性**：测试卡每条断言引用的字段，必须出现在**某个公开返回值**里。引用了内部字段（只存不返的
   `endAtMs` / `pausedRemainingMs` 之类）的断言工人实现不了——要么被迫加宽接口，要么把断言悄悄删掉/降级，
   两种都逃过终审。定稿前拿冻结签名表逐个字段回查，不在任何返回值里的改写成**间接可观测**形式
   （例：不断言 `endAtMs = nowMs + 剩余`，改为 `resumeTimer(1000)` 后 `tick(1000)` → `remainingMs=59000`），
   并在架构/契约文档里写一行「断言可观测性约束：X/Y 不进返回值，禁直接断言」。
9. **卡面命令的可执行性预检**：逐条命令确认 ① **工人沙箱里真有这个工具**——`rg` 不保证存在（用 `grep -nE`），
   沙箱走 PowerShell 时命令形态还会不一样（实测同族：Windows 下 `npx.ps1` 被执行策略拦下 → 工人看到的是「Windows PowerShell
   已禁止运行脚本」这类与代码无关的报错；卡面写 `npx --no-install …` 时要允许**等价入口**：`npx.cmd …` 或直接
   `node node_modules/<pkg>/<cli>.js`） ② 命令要的**依赖已预批准并写进白名单**（如 `vitest --coverage` 需要
   `@vitest/coverage-v8`），否则工人要么违规加装、要么把这条验收静默跳过。
   由**验收方**执行的（覆盖率、全量回归）在卡面里明确标注「由验收方执行、工人不必跑」，别留在工人的命令表里让他纠结。
   再加一条：**每条命令跑正例 + 反例**才算预检通过 —— 只跑正例分不出「命令能跑」与「命令能判真伪」。例：`node --check`（`type=module` 下对合法 ESM 退 0、**对一个故意写坏的语法退 1**，干净目录里两个都跑一遍）。命令本身坏了但看着能跑，工人会照着它把真代码「修」出缺陷。
10. **上游需求条目 → 卡面条目的双向映射**：卡面（尤其**工人**产出的卡面）定稿前，把上游需求 / 模块文档里**每条验收标准**拎出来问「它落在卡面哪一条？」，映射不上就是缺口。
    实测一张界面卡漏了 5 条上游硬项，其中 2 条是上游验收标准的**字面**要求（「列表出现该任务**且输入框被清空**」；以及「添加/勾选/**删除**」里的删除只字未提），
    而卡面只写了「任务出现在列表」—— 只读卡面永远看不出来，必须回上游逐条对。
    反向也要查：卡面每条要求都能追到一个上游依据，凭空虚增的要求同样是缺陷。
    按**内容**对、不按**编号**对：上游 §7 的 T-01 可能是静态检查、卡面的 T-01 可能是浏览器冒烟，编号错位属正常 —— 真正缺的是「内容没覆盖」，补一行映射说明即可。
11. **出卡工人报「上游文档自相矛盾」是资产，不是噪音**：它发现的矛盾要先当**独立裁判**复核，属实就改**源文档**（架构/模块文档）再重出卡，别让卡面单独背着修正 —— 否则下一张卡又从那本坏文档里长出来。
    **同族、方向相反的一条：验收阶段发现的行为变更必须写回冻结规格，卡面同步不算完。** 当工人（或修复轮）改了冻结接口的
    **行为**——校验口径收紧、失败返回值语义、恢复时保留还是重建标识符这类「内部但可观测」的变化——就属行为变更：
    必须写回**权威规格文档**（架构接口表 + 模块稳定决策表），并给它一条可追溯的修订注记（修订 N + 原因 + 位置）。
    理由同上：下一张卡的**出卡人只读卡面与规格文档**，规格不跟上，下游整卡建立在陈旧语义上（实测：出卡轮读到改动前的接口，整卡返工重写）。
    自检问句：**这一轮的改动里，有哪一条是「下一个只读规格的人会得出不同结论」的？** 有就必须同步。
    归属：这类同步是**验收方**的活（工人被禁改规格文档），做完在验收记录里写明「规格已同步至 §X」，
    否则下一位读者会以为代码与规格本来一致，或反过来拿旧规格当权威去回退正确的代码。
12. **静态检查的禁词表只许列「模式」，不许列「合法代码必须引用的标识符」**：禁词的目的是挡住"重新发明业务算术"，
   而不是挡住"读业务层返回的字段"。实测把 `focusMinutes` 列进界面层禁词（本意是防它自算专注分钟），
   而读 `getTodayStats().focusMinutes` 本来就合法且必要 → 工人写成 `stats['focus' + 'Minutes']` 绕过检查，
   检查从此对该文件失效，还留下可读性倒退。正确口径：禁**周期常量与换算形态**
   （`60000` / `workMinutes` / `breakMinutes` / `pomodoroMs` / `cycleMs` / `NN * 60000`），
   标识符只禁"不许出现的方法名/入口"。落地时**先用合法写法跑一遍**，确认检查不误伤它。
13. **卡面命令本身出缺陷时，当轮修卡面源文件 + 用修正后的命令重新取证**：执行工人如实上报
   「卡面第 N 条正则被转义坏了 / 这条命令跑不出真实结论」是**资产**（与 §11 同族）：
   发现即改卡面源文件（否则下一张卡继承同一缺陷），本轮用修正命令重新跑一次，
   **禁**把"工人已按坏命令执行过"当已验收。命令的"正例+反例"预检见 §4.9。
14. **容量型验收样本先自己算一遍（出卡前 + 需求文档定稿时都要算）**：凡验收条写「给定 R 行 × C 列 / N 个样本」，
   先把 `R×C` 与 `N` 的关系、以及这条的**期望措辞**（坐满 / 剩几空 / 前几排满）是否**同时成立**算一遍。
   实测形态：`6×8 = 48` 席却写「40 人全部坐满、无空位」；`3×8 = 24` 席却写「20 人前三排坐满」——两条无论怎么实现都必红。
   不一致必须**在需求定稿/终审前拍板**（改样本数 或 改期望措辞，二选一，并写明保留哪条原意），
   并把裁决同步进需求文档与该卡面。原样往下走，工人只有三条路：照写必红用例、私自改期望、第三种自创读法 —— 三条都白烧一轮。
   推广：任何「样本数 vs 容量」型验收（分页条数 / 批次大小 / 座位数 / 库存 / 并发数）同此办理。

## 五、出卡前的取证（省一整轮的关键动作）

- **卡面写「复用既有 X」时，必须取证 X 的运行时语义**（只读 grep / 读实现），四项任一没取证就会在实现期撞车，
  而每次撞都白丢一轮：
  ① **资源归属**——X 内部会不会终结调用方自己的租约 / 事务（实例：父任务逐候选复用同一 job 的采集入口 ⇒
  第二条必然失租；正解是“每候选开一个子作业，父只管遍历 / 记账 / 续租”）；
  ② **状态载体**——要写的数据有列 / 字段可放吗？既有写路径会不会把它抹掉（“更新分支把 checkpoint 置 None”
  会丢掉刚写入的载荷，而单测仍全绿）；
  ③ **入口存在性**——你以为的“只返回候选”的入口可能只有“搜索 + 逐条采集”的整体入口（正解：整体复用，
  禁在编排层重写搜索、禁为方便另加新入口）；
  ④ **失败路径**——失败时它写不写 `retry_at` / 错误码？不写就永远退避不了，重试只能由上层承担
  （幂等键加后缀 + 重试预算与退避记在上层 checkpoint）。
  取证结论要么直接写进卡面（“租约由父持有 / 载荷存 X 列 / 失败写 Y”），要么在派工单里写明“若与现状冲突：停下报告”，
  不要指望工人自己消化。跨接缝的卡把 **1~2 轮裁定轮**当成正常预算，不当意外。
- **白名单按文件粒度给，并按“必然要动”的范围留最小口子**：对失败路径的退避 / 错误码 / 状态终结这类
  修复唯一可落点的小改，卡面写清“仅限 X 分支”并把它列进白名单；按目录整块禁会把工人逼到合法停摆
  ——守规矩的工人只会报“这属于禁改范围”，而正确的修法被挡在门外（实测为此白丢两轮）。
  （工人侧/验收侧方法论另见 `cli-worker-dispatch`。）
- **卡面技术约束与目标运行环境的兼容性必须探针实测，禁凭记忆**：凡需求写「单文件网页 / 双击可用 / 零构建 /
  离线」，先确认所选技术栈在该运行环境里成立——`file://` 下 `<script type="module">` 被浏览器拦掉
  （ESM 组织方式与「双击可用」直接冲突），ESM-only 的库、`fetch` 读本地文件同理；冲突时**改组织方式，不是改需求**。
- **第三方库可行性四问**（出卡前逐条实测，写进派题/卡面事实基线段）：① 目标环境能否加载（node require / 经典 script）
  ② 关键 API 的真实返回形状与空值表示 ③ **畸形输入是抛错还是静默返回空**——静默返回空的数据，`try/catch` 判不出
  非法文件，错误码与用户提示口径必须另立判据（校验魔数 / 统一按“解析后为空”处理，二选一写死）
  ④ node 与浏览器是否走不同代码路径、需不需要显式注入宿主能力（如 node 侧 `XLSX.set_fs(require('fs'))`）。
  探针配方、双导出写法与探针执行纪律见 `references/zero-build-frontend-and-lib-probes.md`。

- **现状**：凡"现在有没有做某功能"，先 grep 取证，把「缺口 + 证据（`文件:行` 或 grep 输出）」写进派题
  的事实基线段，并点名一条易混淆项（免得架构师以为已做）。
- **外部平台形状**：凡卡面要声明"平台返回什么"，必须**真实抓包/探针实测**并把实测值（字段名+真实值）
  钉进派工单；禁手搓"合理形状"。实测值一律是**形状**（字段是否存在 / 类型 / 单位 / 端口 / 魔数），
  **绝不打印签名 query 或原文**。
- **候选端点要逐个探活，且区分「HTTP 状态」与「body 业务码」**：同平台各端点的可用性互不保证（实测：同一平台
  搜索/热门端点匿名可用，榜单端点 **HTTP 200 而 body 里是风控码**）——只看状态码会把被封的源写进卡面，
  上线才发现整条源不可用。被封的源要作为**取证结论**写进派题：**永久弃用 + 明写禁绕过**
  （不引 Cookie / 不换设备 / 不加代理）；若既有适配器已把它映射成 fail-closed 的业务码，
  **那是正确行为，不许当缺陷派轮去“修”**。
- **同平台不同端点的条目形状可以完全不同 → 卡面逐源钉字段名，禁共用映射**：实测一个列表端点给顶层播放量字段
  与 `"m:ss"` 时长，另一个端点**没有那个字段**、播放量在嵌套 `stat.view`（整数）、时长是**整数秒**。
  卡面必须逐源写清「哪个字段才是真值」，并要求一条用例证明 A 源的解析器不会被 B 源的形状喂饱
  （跨源污染在夹具齐全时看不见，只在真跑时炸）。
- **批次/期号型源要写「新批推进」判据，而不是固定条数**：实测同一源早期批次 8 条、最新批次 48 条，
  实现里写 `len == 8` 会在新批次上 100% 失败。幂等口径写成「出现比已入库最大批号更新的批才抓」，
  条数只作上限断言、不作等式。
- **用户提「不限领域/只靠平台热度」时，先给选项 + 代价再写卡**：纯榜单（领域自适应，但算法池偏头部、
  冷门领域长期不出现）/ 榜单 + 关键词（推荐）/ 纯关键词。选定后：**新源的真实抓包样本先抓后写卡**，
  样本文件随卡入库并写明来源（禁手搓夹具）。
- **工人中途说"真实形状数据不够"时，自己拓样本给它，别让它编造**：抓一份**真实首页全量响应**落成只读夹具源
  （`project/outputs/<卡>_<topic>_sample.json`），**字段名/类型逐字保留**；若需裁剪，**只许减少条数、不得改动保留条目的任何字段值**，
  并在文件内写 `_source`（端点/关键词/排序/裁剪说明）。派题里写清路径 + 「禁手搓、禁改写字段值」，
  并要求交付记录给一节「**真实形状覆盖**」：逐行 `实测值 → 用例名 → 断言`。
  实测价值：工人会如实报「只拿到一条完整投影，其余 19 条没伪造」——把这种诚实变成可核对证据，比让它自己"合理推测"便宜得多。
- **采样设计**：测**分布**用默认/综合排序，测**天花板**再用按指标排序（`order=click` 之类）。
  用"按被测量排序"的采样去测分布，样本会全挤在同一档（实测播放量分布输出 `≥100万 = 40/40`，
  退化成单桶，看不出真实构成）。配方见 `references/real-shape-probing-recipes.md`。
- **抽样 → Top-K 的去重口径必须钉进卡**：分页抽样会**跨页重复命中同一条目**（分页夹具只有一页，工人自测永远不红），
  所以 Top-K 必须先按**自然键去重**再排序取头部；卡面同时要求一条断言**唯一性与排序单调性**的用例，验收时按真跑输出逐项核对。
- **产粮不确定性**：在承诺批量采集前，先交付一个**用户能自己重跑的只读探针**（输入关键词 → 候选上限 /
  规模分布 / 时间分布 / 头部条目 / 一句结论），几十秒否掉没料的领域，省掉整张卡的工人轮次。
- **探针/调试路径与生产路径的容错口径必须一致，并在卡面写死**：探针为了「多看一眼」常对坏条目宽松跳过，
  而生产路径若是整批抛错，探针就永远看不见真实故障（实测：搜索页里混入的一个广告类条目让整批采集失败，
  探针却一路绿灯——差异只在容错，不在数据）。卡面钉死两侧口径：**单条目非法 → 跳过继续**（并记录跳过原因），
  **仅整页/整体结构非法才抛领域错误**；再要求一条用例证明「一页里混入非法条目仍能采到合法条目」，
  否则这类缺陷只能等真实运行才炸。
- **外部规格当需求源**（老师/第三方指导书、接口手册、既有 API 文档）：把它当**待核对物**，不是权威。三步：
  1. **提取冻结物**：把外部文档里散落的方法签名 / 枚举 / 键名 / 数据结构抽成**自己文档里的一节**
     （冻结计数 + 签名表 + 枚举值 + 数据模型示例），卡面从这一节逐字照抄。**禁把外部文档本身当接口依据**
     （写进读取白名单太松：位置会变、内容会被改、且它通常没写清边界返回值）。
  2. **列补钉点表**：外部规格未定义或自相矛盾处，一条一行「外部原状（引原文位置） | 本处冻结」，钉进架构文档
     并回引到卡面。**禁默默按一种理解实现**——同一处两种读法会在卡与验收之间劈出裂缝，验收时两边各按自己的读法判。
     四类高频：① 枚举值与示例输出打架（正文说三种状态，示例里出现第四种）② 同一量有两处载体
     （两个计数器 / 两处字段，谁是真值未定）③ 文档要求的行为**没有落点字段**（要求「记录剩余毫秒」但模型里没这个字段）
     ④ 文档内部命名/调用形态自相矛盾（一处 `timer.tick()`、一处写在实例上）。
   ⑤ **无参方法却要产出依赖上下文的值**：文档要求 `pauseTimer()`（无参）「记录剩余毫秒」，签名却拿不到当前时间
     → 必须钉死**实例内部缓存字段**（如 `lastNowMs`）与「它由哪几个方法更新」「从未收到过时间时取值为何」；
     同族：文档没说 `reset` 是否连带清空累计计数、`start` 在非 idle 时是否生效——**这类边界语义一律显式写死**。
     不写，工人只能自己猜一种，猜错要在验收时才发现（而且两边都自认按文档做的）。
  3. **落实中发现新条目要回填，并把实际条数如实写进文档**：首轮比对列不全很正常。写「初版 3 条，逐条落实时又发现 3 条，
     共 6 条」，比一个假装完整的数字可信，也提醒下一次别把首轮清单当全集。
  补钉原则写死：**只补未定义/自相矛盾处，不改外部给的验收口径与步骤顺序**（改了就不是完成同一件事了）。

## 六、用户中途口述的「产品意图」⇒ 先落决策文件，再谈立卡

用户突然解释某个既有入口/输入"是干嘛用的"（如"这个 URL 就是给用户复刻心仪爆款的"）——这是**需求级**
信息。落 `project/decisions/decision_<预留卡号>_<topic>.md`：

1. **逐字保留原话**，紧接"回读后的正式含义"，把口语转成**可验收**表述（本例：建议必须挂在被指定案例的证据上，
   禁无证据空话）。
2. **现状盘点表**：`环节 | 状态(✅已合入 / 🔄在卡 / ❌缺口) | 依据(卡号 + commit 或符号)`；
   **先 grep 需求/架构文档确认缺口真实存在**，别凭印象宣称已覆盖或已缺口。
3. **建议下一步（待 🟢）**：依赖是否就绪、建议顺序（**先合当前卡再立新卡**——新能力要拿真实样本验收，
   样本不足时做出来也验不了）、行为组候选、真跑口径、边界与不变项；显式写明**不升级为批准**。

纪律：**不把新意图硬塞进正在跑或已终审的卡**；缺口是否单独立卡由用户拍板。落成决策后要在
快照/模块索引留一行指针，否则下次会话找不到。

## 七、常见坑

- `grep -c` 数组数（见 §4.1）；按字节量卡面（见 §2）。
- **表格里含 `|` 的命令会撑破表格**：`grep -nE 'a|b'` 这类命令写进 markdown 表格后，渲染与工人复制都会截断
  （少读一个枚举值 = 少一条断言）。凡命令里有竖线，就用 fenced code block 单独给出，表格里只写「见下方代码块」。
  **转义不算修好，反而更坏**：表格里把竖线写成 `\|` 能让渲染正常，但工人是**照抄单元格文本去执行**的 ——
  拿到的是 `\|`，正则从「或」变成「匹配字面竖线」，检查**恒不命中**、照样打印 `NONE`、退出 0。
  这种「有输出、其实什么都没查」的空检查比缺检查更危险，因为验收方会据此判过（实测：界面卡的业务常量扫描空转一整轮）。
  判据：命令里出现 `|`、`&`、`>`、`$(`、嵌套引号时一律进代码块。
- 压缩轮会顺手丢东西：压完必做 §4.3 点名标识扫描。
- 两份卡对同一参数给出不同数值 → 定时炸弹；参数只能**一处**权威定义，后卡取代前卡时要在后卡写明"同步修改
  `<前卡产出文件>`"并把它列入白名单（**不改前卡卡面**）。
- 别自己替架构师定稿卡面去"省一轮"：卡面是待审物，有矛盾就派微修轮并把裁定写进派工单。
- 终审包只端三块（最终卡面 / 验收 GWT / 禁止行为）；不要把整篇裁决倒给用户。

## 八、验收侧固定动作：**验收方亲自跑一次真跑**

pytest / 覆盖率 / lint 全绿**不等于**功能可用——实测一张卡在「全量回归绿 + 覆盖率五项达标」的状态下，
真跑仍挖出 **8 个自动测测不到的缺陷**，且几乎全落在**接缝**上。凡卡含外部 IO / 跨模块接缝 / 新 CLI 入口，
验收必须由验收方亲跑**真入口**（用户会执行的那条命令）并登记「真跑缺陷」清单。

四类反复出现的盲区，逐张卡对照：

| # | 盲区 | 表现 | 单测为何看不出来 |
|---|---|---|---|
| ① | 配置解析 | 校验器只认原生类型 → 真跑以环境变量字符串注入时**构造期**就炸 | 单测直传 int，全绿 |
| ② | 错误码归因 | 框架把领域异常包成校验异常 → CLI 只报兜底码，丢掉稳定错误码 | 单测直接调领域函数，不经过装配层 |
| ③ | 解析器形状 | 端点返回的元组被整个当成数据落库（"候选列表"长度 2、两个元素都非法） | 夹具恰好是同一错误形状 → **假绿** |
| ④ | 入口覆盖 | "离线 E2E 通过"其实跑的是内部函数、绕开了真实入口 | **覆盖率报表是最快的识破手段**：入口文件覆盖率个位数 |
| ⑤ | 持久化/恢复 | 真刷新/重启后**累计计数被多算**（实测"番茄 +1、专注分钟 +25"），或持久化结构漂移 | 单测从不重载：同一进程里被测对象一直是内存态；静态检查只看语法与禁用 API |

⑤ 的固定动作：验收方**自己真重载一次**（刷新页面 / 重启进程 / 重建活动对象），把重载**前/后**的
剩余时间、累计计数、持久化**键名与形状**并列比对；重载本身不得改变任何累计计数，持久化结构必须逐个键
对上冻结数据模型。根因常在卡面：**业务层冻结接口没有恢复入口时，界面层只能自己重算业务算术**
（判定句：*这个状态由谁负责重建？* 答案应是业务层的一对 `snapshot()` / `restore()`，
不是让 UI 层复算周期与计数 —— 后者即使这次算对被修好，下一个改动仍会再错，且无法单测）。

**真浏览器验收本地页面时，先把环境排除干净**（否则环境问题会被误判成产品缺陷）：起服务前
`netstat -ano | grep ":<PORT>" | grep LISTENING` 确认端口没被**上一轮遗留的静态服务**占着 ——
实测旧服务仍在服务**已被删掉的目录** → 目标页稳定 404、`getElementById` 全 null，
**看起来像「工人一个元素都没写」**，而新服务绑不上端口静默退出；再逐个资源
`curl -sS -m 10 -o /dev/null -w '%{http_code}'` 确认 200；断言 DOM 前先打印
`location.href` + `document.title` 确认自己在目标页上；收工按 netstat 的 PID 列逐个
`taskkill -PID <pid> -F`（杀启动器 PID 会留下子进程继续占端口），杀完复核监听计数为 0。

**纯文本渲染（禁 `innerHTML`）要靠「真的没被当 HTML 解析」来判，grep 只能证明源码里没有那四个字母**：
真浏览器三连断言 —— 注入 `<img src=x onerror=alert(1)>` 后 ① `querySelectorAll('#task-list img').length === 0`
② 先把 `window.alert` 覆盖成计数器，断言未被调用 ③ 该行文本节点原样回显（`.childElementCount === 0`，
证明是 `textContent` 写的纯文本）。三条合起来才排掉"标签被解析但事件没触发"这类假绿灯。

**驱动脚本自身的缺陷会伪装成产品缺陷 —— 判「异常」前先证明你的驱动那一步真的生效。**
实测形态：程序化给 `<select>` 设了一个不存在的 `value`（被浏览器归零）→ 页面**正确地**报「请选择有效的列」，
而报告写出来像「选了列仍不能生成」，差一步就把验收方自己的脚本 bug 记成产品缺陷。
固定动作：把驱动那一步的**输入值 + 事件是否派发 + 页面状态快照**各打一次，再判定。
本地零构建页面的完整 CDP 驱动配方（上传夹具 / 复制 / 打印 / 离线 / 注入式入口 / 竞态 / 性能）
见 `references/zero-build-frontend-and-lib-probes.md` §7。

**多轮文档交付被掐断时，验收动作是「冻结值逐字交叉核对」，不是对数行数**：跑一份小脚本，把权威文档里每条冻结值
（函数名 / 入口名 / 错误码文案 / 枚举候选 / 上限）逐个 grep 进**每一份**派生文件（模块文档、卡面、AGENTS.md），
逐条报命中/缺失。只查「文件存在 + 行数 + 章节齐」会漏掉**陈旧行**：派生文件里仍写着「XX 未冻结 / 原文待定」
而权威文档早已冻结 —— 两处自相矛盾，下一张卡就照陈旧的那句写。
缺口按**行号级微修轮**处置：派题里逐条写「第 N 行 现状 → 改成」+ 2~3 条自查 grep（如「`原文待定` 计数必须为 0」），
并用**最低档模型**跑（纯逐字替换、判据已被行号钉死，不值得高 effort）；**禁**因收尾被掐断就重派整轮。

配套：真跑验收的卡面口径（真入口/真形状/真状态/真注入、每条声明路径各跑一次、真中断）见 §三；
工人侧与验收侧的派工方法论见 `cli-worker-dispatch`。

**验收前的取证与归因**（白名单外文件被改怎么归因、怎么解析 codex rollout 取工人真实工具调用、
零输出挂死怎么定位、工人产出文件的 BOM/UTF-16 编码坑）见 `references/worker-attribution-and-artifact-forensics.md`。
归因纪律一句话：**先写证据再记越界**——mtime 与工具调用审计都不指向工人时，不得按「越界即暂停路线」处置。
