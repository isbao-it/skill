# 开发模式：不变量、模式参数、模式表与门禁

配套 SKILL.md。用于**用户要换开发模式**或改流水线结构时。

## 1. 现有条文归类示例（判类法的实操）

| 条文 | 类别 |
|---|---|
| 未终审不派工；未手测+审核不 commit | 不变量 |
| 三级审核（初审独立裁判 + 用户终审三块） | 不变量 |
| 双重验收（AI 测 + 用户手测） | 不变量 |
| 薄卡预算 8000/6000/14000；关键常量钉死 | 通用 |
| 额度与上下文纪律（轮数预警、读取白名单、输出重定向、验证外包、产出瘦身） | 通用 |
| 用量口径（分段求和、缺失记 null、探针不计卡成本） | 通用 |
| 质量度量指标 | 通用 |
| 分层测试强度 90/80/60 | 通用 |
| 拆卡成本门槛、出卡会话默认新开 | 通用 |
| **滚动双卡：出一张审一张，禁止批量攒审** | **模式参数** |
| **并行上限 1 执行卡 + 1 草稿 + 1 验证进程** | **模式参数** |
| **单卡全链路预算表（含"按单卡计"的口径）** | **模式参数** |
| 按依赖顺序推进、任务/模块/项目三级闭环 | 半通用：闭环要求通用，"同时只有一张卡在跑"是模式参数 |

## 2. L1 模式参数（模式卡只写这 9 项的差异）

| # | 参数 |
|:-:|---|
| 1 | 出卡节奏（一张一张 / 接口冻结后一批 N 张） |
| 2 | 并发度（同时几张卡、几个工人；受额度桶截断） |
| 3 | 卡粒度（完整卡 / 一片一卡，片含"本片验收命令 + 依赖的片"） |
| 4 | 前置物（模块文档 / 接口冻结物 / 各片 worktree） |
| 5 | 验收粒度（卡级 / 片级自验 + 装配片总验） |
| 6 | 合入方式（滚主干 / 分支 → 装配片收口 → 一次合入） |
| 7 | 额度口径（按卡 / 按迭代包） |
| 8 | 止损（连续 2 轮无实质产出换策略 / 并回主工作区升一档一轮收口） |
| 9 | **迭代包（时间盒）**：一个包 = 一组卡 / 一个时间窗，包内可并行、包末总验（M1 不切包；M2 = 1 包 N 卡 / 1~2 周；M3 不适用） |

> 用户问「我是不是还停在瀑布、要不要上敏捷」时的口径：**敏捷只取两样**——批量大小与反馈回路（他已有），
> 不取站会/速度/自组织这类仪式；真正缺的是**第 9 参数（时间盒）**。引入它之后 M2 才从"同时跑几张卡"
> 变成"一个时间盒交付一组增量"，验收粒度与额度口径随之按包计。

## 3. 三个模式

| 参数 | M1 滚动单卡 | M2 敏捷并行 | M3 探针/弃子 |
|---|---|---|---|
| 出卡节奏 | 一张一张 | 接口冻结后一批 N 张 | 1 张，不进卡目录 |
| 并发度 | 1 执行 + 1 草稿 + 1 验证 | N 片并行，N ≤ 并发额度余量 | 1 |
| 卡粒度 | 完整卡（执行卡 + 测试卡） | 一片一卡 + 本片验收命令 | 可弃脚本 |
| 前置物 | 模块文档 | 模块文档 + 接口冻结物（端口签名/契约清单/冻结计数）+ worktree | 只读夹具 |
| 验收粒度 | 卡级 | 片级自验 + 装配片最后总验 | 探针结论，人工看数 |
| 合入方式 | 滚主干 | 分支 → 装配片收口 → 一次合入 | 不合入，结论入库 |
| 额度口径 | 单卡预算 | 迭代包 = 单卡预算 × N，按桶分 | 一次小额 |
| 止损 | 2 轮无产出换策略 | 任一片卡住 → 并回主工作区升一档 | 时限到即弃 |

M2 的切片/止损/装配片规则**已存在于卡面技能**（`task-card-authoring-and-audit` §一）：
"本片在自己的 worktree 里能跑完自己的验收命令吗""接口冻结 ≠ 实现就绪""编排/装配类片天然是最后一片"
"同一片连续 2 轮无实质产出即换策略、禁第 3 次原样重派"。模式卡只是把它们收编成一种可选模式，不是新发明。

## 4. 选模式判据（不是"项目不同"，是三个变量）

1. **接口定型程度**：端口/契约未定型、架构暗雷多 → M1；接口已冻结且有冻结计数可核对 → 可上 M2
2. **片间耦合度**：有共享文件、跨片"预期红"穷举不完 → M1；无共享文件、每片能独立真跑 → M2
3. **可用并发额度余量**：只够 1 路 → M1（并行只是排队）；够 ≥2 路才谈 M2（同账号多路并发亦可）

判定顺序：是否只回答**一个未知量**（第三方端点形状、库可行性、性能天花板）→ 是则 M3，别立卡；
否则看接口是否冻结 → 未冻结 M1；已冻结再看耦合与并发余量。

> 反例依据：某张卡在"全量回归绿 + 覆盖率五项达标"下真跑仍挖出一批缺陷，**全部落在接缝**。
> 并行只会把接缝数量乘上片数 —— 所以 M2 的门禁是硬门禁。

## 5. M2 启用门禁（6 项，缺一不启用）

1. 接口冻结物存在（端口签名 / 契约清单 / 冻结计数）并被卡面引用
2. 每片能独立真跑：逐片回答"这片在自己的 worktree 里能跑完自己的验收命令吗？"
3. 并发额度余量 ≥ 片数，并写明每片用哪个账号/工人 + 当前余量证据
4. 装配/编排片已识别并排在最后（不与实现片并发）
5. 各片 worktree 就绪：`.gitignore` 覆盖 `.pytest_tmp-<卡号>/`（Windows 沙箱 basetemp 权限坑），
   且每片 worktree **能直接跑起自己的验收命令**——依赖目录用**目录联接共享主仓**而不是各装一套
   （Windows：`node -e "require('fs').symlinkSync('<主仓>/node_modules', '<worktree>/node_modules', 'junction')"`；
   git-bash 里 `ln -s` / `mklink` 不可靠）。**共同基线（依赖清单 + 锁文件 + 测试运行器与覆盖率插件 +
   vendored 第三方库 + 夹具 + 冻结文档的仓库内副本）必须先落盘并 commit**，各片从同一个 SHA 长出；
   判定句：*这条验收命令，在刚拉起的干净 worktree 里能直接跑吗？*不能 → 先落基线。
6. **装配片的口径单独写清**：它在自己的 worktree 里**无法独立真跑**（要另外几片才成产品）→ 卡面写「本片验收 =
   上游回归不破 + 静态自检，端到端/浏览器真跑由验收方执行」。不写，工人会拿一个注定达不到的口径把自己判死。
   合入走「各片分支 → 装配片分支收口 → **一次合入主干**」，**验收通过的各片分支不单独合入**。

## 6. 模式怎么记

- 《需求与范围确认》勾一行「开发模式：M1/M2/M3」——给人看
- 项目内一份 `PROJECT_MODE.md`（或架构文档头部一段）——给会话读
- 换模式的原因记一条决策文件（`project/decisions/`），不要只留在聊天里

## 8. 换模式/改流程的爆炸半径（改一处必查全套）

| 文件 | 同步什么 |
|---|---|
| 权威原文 | §模式选择 勾定当前模式 |
| vault `.hermes.md` | 「流程骨架」一行（常写死"滚动双卡"）+「额度纪律」里的并行上限 |
| `Templates/需求与范围确认模板.md` | 加一行「开发模式」 |
| `Templates/任务卡片模板.md`、`测试卡模板.md` | 并发模式需加「本片验收命令 / 依赖的片」两栏 |
| skills（卡面侧） | 只留指针，规则只在权威原文定义一处 |
| 派工命令里的模型名 | 常与最新分工脱节，属独立议题——**改前先问用户** |

## 9. 交付形态与常见坑

- 方案稿落 `_Outputs/待审核/<主题>_<日期>.md`；六块结构见 SKILL.md §5
- 分块写（每块 ≤3KB）→ 合并 → 读回核对**字符数 + 章节清单 + 末行**；只核对"写成功"不算核对
- 正文改动量要估算给用户（动几处、新增几个文件），并在方案里标「未验证」项（如新模式无实战、并发额度余量未探活）
- 未实战的模式必须在文件里标"未验证"，不要把推演写成已验证结论
- **第一步落地形态**（用户认可以后）：① `modes/README.md` 承载 §模式选择 成稿 + 三模式一览 + 9 参数清单 + M2 门禁 + 待办表；
  ② `modes/M1_<模式名>.md` 把**现行做法原样收编**（零行为变化）——每个参数附**正文行号**做证据，可逐条回查；
  ③ 正文与 `.hermes.md` 暂不动，并在新文件头部写死"冲突以正文为准"。**收编 ≠ 重写**：M1 卡只做归位，不改任何要求。

## 10. 方法论定位（回答"我是不是瀑布 / 要不要上敏捷 / SDD"）

别用"瀑布 vs 敏捷"这个轴，用四个变量定位：

| 变量 | 本用户现状 | 判定 |
|---|---|---|
| 批量大小 | 滚动单卡、禁批量攒审 | 小批量（敏捷特征） |
| 反馈回路 | 每卡双重验收 + 用户手测 ≤5min | 短回路（敏捷特征） |
| 规格前置 | 架构一次定稿 → 模块文档 → 双卡 | 瀑布特征，且对本场景**有意为之**：工人是无记忆的 LLM，它的记忆就是文档 |
| 变更成本 | 执行期改需求 = 退回待执行；追加需求流程只覆盖架构阶段 | **唯一真正的瀑布残留** |

结论：**规格驱动 + 滚动增量 + 阶段门**——不是瀑布（无一次性交付、无跨团队阶段交接），也不是敏捷（无时间盒）。

SDD 分级：spec-first → **spec-anchored**（他在此）→ spec-as-source。停在 spec-anchored 是安全的
（spec-as-source 要求完全信任一个本质不确定的生成管线，不纳入）。两条可引用的判据：

1. **成本判据**：修规格的成本必须低于修实现误解的成本，一旦反过来就是过度规格化信号——薄卡预算就是它的量化版。
2. **通病**：此类流程的主要失败模式是 agent "context blind"（幻觉 API、架构越界）→ 修法是**只读探针做 grounding**
   + 每份中间产物做 validation；他的"出卡前取证 + 冻结计数双向核对"已是此法。

所以他缺的不是 SDD，而是**规格的单一事实源**（架构文档/模块文档/卡/`.hermes.md` 四处并存 → 漂移）。
