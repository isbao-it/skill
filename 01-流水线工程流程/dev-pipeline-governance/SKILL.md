# 流水线治理：层级对齐、不变量 vs 模式参数、开发模式选择

适用两类活儿：

1. **按用户的流水线干活**（<user>的自动化开发流水线：任何在跑卡、派工、验收的会话）；
2. **改流水线自身**——换开发模式（滚动单卡 / 并行切片 / 探针）、加门禁、调额度纪律。

工人侧/验收侧方法论见 `cli-worker-dispatch`；卡面侧见 `task-card-authoring-and-audit`。
本技能只管**流水线这一层**怎么才算对齐、什么能动什么不能动。

## 0.5 分层总览（2026-10-08 新增，规则以正文为准）

| 层 | 一句话 | 权威位置 |
| :-: | --- | --- |
| L0 不变量 | 先审后动 / 白名单 / 自报不可信 / 真跑 / 越界=0 | 正文「L0 不变纪律」 |
| L1 阶段层 | 0→6 阶段 | 正文「完整阶段流程」 |
| L2 模式层 | M1/M2/M3（9 参数） | 正文「模式选择」+ `modes/` |
| **L3 规模层** | **S（≤2 片）可省模块文档与 M2；M（3–5 片）模块文档降级；L（≥6 片）全流程** | 正文「规模层」 |
| **L4 契约层** | 冻结节唯一权威 → `frozen.lock.json` → **只引用不抄写** → **验收前跑 `tools/frozen_check.py check`** | 正文「契约层」 |

> 两条实测结论：① M2 不是省钱模式（首轮 6.50 M input vs 番茄 5.44 M），是**省时间/降返工**模式，48% 花在"前置费"上 —— L3 就是判断这笔钱该不该花；② M2 的错集中在**文档层**（没有测试会红），L4 的机器校验是唯一防线。

## 1. 先对齐权威层（动手前必做）

规则同时存在于四层，**冲突以第①层为准**：

| 层 | 位置 | 性质 |
|---|---|---|
| ① 权威原文 | vault `4-Projects/自动化开发流程/软件开发自动化流水线.md` + `Templates/` + 调度手册 | 唯一权威 |
| ② 会话执行摘要 | vault 根的 `.hermes.md` | 每会话注入，自称"冲突以原文为准" |
| ③ 硬守卫 | `hooks.pre_llm_call` → `agent-hooks/pipeline_guard.py` | 未终审禁派工、未手测+审核禁 commit |
| ④ skills | 本技能等 | 方法论，**可能有旧版副本** |

- ⚠️ **skills 层可能存在旧版流水线**：description 最像"自动化开发流水线"的那个不一定是最新的。
  照它执行前与①比对三处最容易停在早期版本的地方：**工人档位、架构角色归属、额度纪律**。
  实测存在只有"单一工人 + 由我直出架构"的旧副本——命中就走旧流程。发现新旧冲突：**报告用户，不要自行按旧版执行**。
  **旧副本的 description 自己就会露馅**：把工人写成单一 CLI（如「Claude Code 做程序员」）、把架构归给 Hermes/助理、
  没有 M1/M2/M3 字样的，基本都是早期版本——不用读完正文就能判。
- 项目级 `AGENTS.md` 是第⑤类（项目特有）；与①冲突时以①为准并回报。
- 会话开始涉及开发任务时：读 `_Tasks/待执行/` 与 `_Tasks/执行中/`，确认有没有在跑的卡，再决定能不能动。
- **产物落位**：项目仓库里流水线工件放 `project/`（需求与范围确认 / 需求分析与架构方案 / `modules/` 模块文档 /
  `cards/NN/`（任务卡+测试卡+`dispatch.md`）/ `outputs/NN/<run_id>/` / `decisions/`），应用代码在仓库根，
  **唯一 `run_id` 的证据目录由派工方预置**（派工前创建并写进派题，含 `summary.json` / `结论.md` / `details/`）：
  工人的白名单只包含「代码文件 + 该证据目录」，目录不存在时它只剩越界创建或把证据写到别处两条坏路；
  并发片各取时间戳命名还会撞名 —— 唯一性归派工方定，不是工人自选。
  仓库根放 `AGENTS.md` 作**工人自动读取**的项目级约定（分层红线、接口冻结计数、只动白名单、禁 git、中文注释）。
  **若项目本身自带一份交付物文档目录**（课程作业要求的 `docs/`、客户要的 `doc/`），
  流水线工件不要混进去——交付物要能原样提交、原样交出去，别把工程过程文档塞进别人要评的东西里。
  卡面「输入文件」白名单要指向 `project/modules/<模块>.md` 与 `AGENTS.md`，不要让工人去啃整份架构文档。
  **工人沙箱只覆盖项目仓库**（`codex exec -C <项目根>`）：凡卡面/派题要求工人阅读的 vault 资产
  （`Templates/` 两份卡模板、模块文档模板、老师指导书），先**复制进 `project/templates/`** 再写进读取白名单；
  漏这一步工人只能凭记忆猜模板结构，或越界去读仓库外文件——两条都是红线。

## 2. 每条规矩先判类（防漂移的核心动作）

自问：**换个项目、换个节奏，这条还成立吗？**

- 成立 → **不变量（L0）** 或 **通用**（与模式无关）
- 只在特定节奏下成立 → **模式参数**，归模式卡，不许写成"铁律"

把"禁止批量出卡""并行上限 N""按单卡算预算"这类**模式参数**写进铁律章节，是流程漂移的根因：
真要换模式时只能去改铁律，过一阵就分不清哪条是底线。

**L0 不变量（任何模式都不得削弱）**：未终审不派工；未**验收通过**不 commit（`#审核通过` 即可；手测非必需——能自动化的含 UI 由验收方真浏览器自跑，够不到才请用户手测，用户明确要求「非必要不要让我手测」）；**AI 测不通过的产出不端给用户**——
先把失败证据 + 修复方案（含「修哪一层」的选项对比与推荐项）端上去要一个批准，别让用户去手测/终审一个已知不合格的产出；工人只动白名单；
验收方自己复跑、不采信自报；越界/放水=0、关键漏测=0；每份产出留 `summary.json`+`结论.md`+`details/`；
薄卡预算与关键常量钉死；用量口径与质量度量。

**人的验收注意力四桶（按序）**：① 不可逆与钱/法律（删数据、迁移、密钥、外部账号风控、失控的外部付费调用）
② 安全边界（跨层调用、注入、越权、SSRF、不回显原文）③ **接缝与真跑**（装配、配置注入、错误码归因、真实数据形状、真实中断态）
④ 规格-代码一致性（冻结计数、跨卡残留断言）。**风格/格式/复杂度交给工具**（ruff + 分层守卫测试），不占人脑；
禁把通用 Web 清单（支付幂等、CORS）搬进没有支付的项目——按该项目真实的不可逆面重述。

## 3. 换模式前先数额度桶

**并行度上限由可用额度余量决定，不由流程决定。** 同一 CLI 账号可多路并发（2026-10-08 实测：同账号 2 路正常），但它们**共用同一个额度桶** —— 可见剩余 <20% 即退回串行；
并发余量 < 片数还说"N 片并行"，结果是排队 + 接缝风险乘以片数（接缝是本用户项目里缺陷最密的区域）。
选模式的三个变量、M1/M2/M3 差异表、并行启用门禁见 `references/pipeline-mode-layering.md`。

**并发余量之外的第二笔开销是「档位」——分配档位就是分配额度。**

- **额度按「模型档位 + reasoning effort」扣，不按 input 大小**：实测同一天 `sol`+`high` 的 9 个用量事件 = 5h 窗口 **+5 点**；
  `luna` 122 个事件 / 544 万 input 也才 **+5 点**（差约 10 倍）。→ **禁**用 token 数或缓存命中比例换算额度节省（口径不同），
  要判成本就量百分点。
- **派每一轮前先答一句：这轮产出的是「判断」还是「提取」？** 判断类（出卡、架构、跨卡裁决、复杂失败诊断）给 `sol`；
  **提取/替换类（模块文档、错误码表、文案同步、按行号微修的字段替换）一律 `luna`，禁 `sol`** —— 把提取类派给 sol 是纯白烧。
- **effort 默认 `medium`**；只有「新栈首次落地 / 架构分歧大 / 跨卡冲突」才升 `high`，且必须在派题里写明**为什么需要 high**（写不出就降档）。
- **省钱优先级：① 别把非判断类活派给 sol ② 合并轮次 ③ 才轮到换模型/换工人。**
  合并排第二的理由：每轮都有启动溢价 + 约 20k 的规则/AGENTS 底噪，两轮本可一轮做完的文档 = 多付一次启动钱。
- **中断的轮次不要顺手补活**：缺口再小也派一轮最低档微修（判据已被行号钉死，不需要判断力），
  调用方直接改产物会失掉「谁写的谁修」与独立验收两条边界。
- 度量配方：`scripts/quota_delta_by_round.py [YYYY-MM-DD]` 逐会话打印「模型 / 用量事件数 / primary 起止百分点 / Δ」；
  input 口径另用 vault 的 `tools/codex_usage.py --since <日期>`。**两个口径分别看，不要相加或互换。**
- **用户说「消耗好大 / 是不是这个模型贵」时，正确回应顺序是：先量（逐轮 Δ）→ 再定位错配 → 再给档位表修订建议（带选项与 WHY）**，
  而不是先解释「其实不贵」——用户的体感常常来自「看得见的逐轮报账 vs 闷头滚」，把量出来的数摆上去，再谈要不要降档。

- **用户点名的模式不豁免判据**：先按判据表（接口定型程度 / 片间耦合度 / 可用并发额度余量）逐项复核，**冲突时给选项、
  把「回退默认模式」列为推荐项**并附一句 WHY；照办与擅自改判都不行——两者都替用户做了决定。
  实测：用户点名并行模式，复核发现只有 1 个桶，端出三个选项后用户自己改判回默认模式。
- **门禁是 AND，不是加分项**：接口冻结补不了额度余量，余量够也补不了接口冻结；任一不满足即降级，
  并要求文档写出「所以判到 X 模式」的**推导链**（逐项取值 → 结论），别只写结论。
- **门禁全过也要交代成本，让用户在知情下拍板**：判据通过 ≠ 无脑照办。若用户点名的模式在本项目体量下
  **编排开销大于收益**（片数少、总量小、大多活一片就能干），照办的同时用一句话说明「你在买什么」
  （如“M2 的 worktree + 包末总验开销大于收益，跑它的价值在验证流程而非交付速度”），并把回退默认模式列为备选。
  既不擅改判，也不替用户决定他要不要花这笔成本。
- **把「规矩」讲成「技术封锁」是错的**：额度/并发类追问题时，先把三件事拆开回答 —— ① 技能上能不能（并发路径是否走得通）
  ② 本账号当前余量够不够（看 5h/周窗口实测百分比）③ 流程纪律该不该（同一额度桶共用、撞限时账号级全拒）。
  拿纪律当技术上限回复，会被用户一句「不能吗」当场推翻（本机实测：用户追问后跑一次并发探针即证伪）。
  用户追问时**先跑探针拿实测再答**，并把新事实回写成条款（可能就要改流程本身）。
- **改判要落进「确认记录」**：需求确认文件的确认记录里写一行（原选 → 改判 + 依据），否则下一会话只看得到结论、
  看不到为什么，很容易又按用户原话把模式改回去。

## 4. 改流程 = 四层同步，只改一层等于没改

权威原文、`.hermes.md`、两份卡模板、项目规则、skills 指针 —— 漏一层，下一会话按旧层执行。
完整爆炸半径清单、模式选择节该放什么、建议的 modes/ 目录结构，见 `references/pipeline-mode-layering.md`。
**规则只在权威原文定义一处**，skills 里只留指针，否则又是新的漂移点。

- **同步前先分清「规则定义」与「事故记录」**：同一句话往往出现在两类段落里 —— 规则定义（判据表、门禁、模式卡参数）必须全部改到；
  而**事故记录/坑清单里引它当理由的**，先看那个理由本身是否仍然成立。
  例：把「同一账号只跑 1 个任务」额度口径的地方要改；但把它当作「别让两个进程写同一仓库」的理由处，
  理由仍成立、**禁顺手改**——改了会抹掉那条教训的因果（下一位读者不再知道为何当初要串行）。
- **改完用一条 grep 扫旧口径**（正文 + `.hermes.md` + `modes/` + `skills/` 四层一起），确认零残留；
  残留一条，下一会话就按旧层执行。
- **判据条款必须自活数（带实测依据）**：改写「上限/阈值」类条款时把实测写进句子（如「同账号 2 路并发正常」），
  否则下一位读者会当成未验证的口头约定而回退它。

## 5. 流水线自身的改动怎么交付

- 落 `_Outputs/待审核/<主题>_<日期>.md`；**不直接改权威正文**——正文改动是另一个动作，要单独 🟢
- 编号章节，六块齐全：现状诊断（带行号）→ 差异表 → 待用户拍板决策（每项带建议）→ 分步落地 →
  风险与未验证项 → 明确不做
- 「明确不做」写死：不改正文、不建目录、不动 skills、不 commit
- 长文**分块写**再合并，合并后读回核对字符数 + 章节清单 + 末行（vault 长文写入偶发静默截断）。
  **单文件追加法（无中间件，适合 4~10KB 的文档）**：第一块 `write_file` 落盘并以**唯一哨兵**结尾
  （如 `<!-- CUT -->`），之后每块用 `patch` 把哨兵换成「本块正文 + 哨兵」，最后一块换成收尾正文；
  收尾用一句话核对：`assert '<!-- CUT -->' not in text` + 报 `len(text)`。
  **哨兵仍在场 = 那一块没写完**（静默截断的最快判据，比通读快）；哨兵已消失同时证明每块都替换成功
  （`patch` 匹配失败会直接报错，不会静默跳过）。
- **中段插入新节要重整后续编号**：从分块源按标记切分重组（切分点先 assert 再覆盖目标文件），
  不许把新节追加在结尾「明确不做」之后；重组后重列章节清单，确认编号连续
- 决策表**每项带「我的建议」列**：用户回「按建议」= 按整表执行，但落地仍只做最小一步
- 结尾只推**最小一步**（零行为变化的那一步通常先做），不要一次推全套
